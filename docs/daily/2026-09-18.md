### [cloudflare/security-audit-skill](https://github.com/cloudflare/security-audit-skill)

 `JavaScript` ⭐ +3,607 今日新增 · 11,017 总星数

> Cloudflare 开源的编码 Agent 技能，把安全审计拆成六阶段，用独立 Agent 反驳候选漏洞，产出机器可读的漏洞清单。

**亮点**

- 把'覆盖范围'做成一等公民：先落 coverage-ledger.json 再动手，用 critic 补漏，承认单次审计覆盖不全并靠重复运行补齐——这是对 LLM 审计容易漏区这个具体毛病的直接解法。
- 默认不执行被审计代码：没有 OS 级沙箱（断网、白名单环境变量、资源限额、只能写临时目录）时，所有涉及构建/测试/fuzz 的线索一律停在 needs_validation，不给 confirmed。

**核心功能**

- 六阶段流水线：侦察写 architecture.md → 按 coverage-ledger.json 分单元派独立 hunter → 每条候选漏洞交给新 Agent 反驳 → 写 findings.json 并用 Node 零依赖脚本卡 schema 校验 → 换一批 Agent 复核结论来源 → 生成报告。结论必须带完整代码溯源，否则只能标 needs_validation。
- 对抗式验证：查漏洞的 Agent 和验漏洞的 Agent 不是同一个，验证者拿到的是全新上下文，任务是试着证伪。needs_validation 状态不允许标严重等级，逼着人把未解决的事实写清楚，而不是猜一个风险值。
- 覆盖账本 + 增量运行：先把仓库拆成覆盖单元记进 JSON，用 coverage critic 找漏掉的区域；同一仓库多次跑结果叠加，靠旧账本补空白、只重验改过的源码。作者实测跑一遍只能找到重复跑总漏洞量的一半左右。

**适用场景**: 安全工程师和研发团队在发版前、接外部代码或做合规审计时用；手里有 Claude Code 一类支持子 Agent 的编码工具、想让 Agent 系统性地过一遍自家仓库的人。

**竞品对比**: 和 Semgrep、CodeQL 这类靠预写规则或查询语言的 SAST 不同，它不依赖规则库，而是让 LLM 分阶段探索再用独立 Agent 证伪。和 XBOW 这类 AI 渗透测试产品比，它跑在代码仓库上而不是线上目标，且强制产出可复核的 JSON 记录。相比'直接叫 Agent 读代码找漏洞'，多了覆盖账本和 schema 校验两道约束。

**成熟度**: 早期项目：没有版本号，只有技能文档加两个零依赖 .cjs 校验脚本（带单测），要真正跑执行类验证得自备沙箱；但源码来自 Cloudflare 已上线的内部漏洞挖掘 harness，有官方博客背书。

**趋势信号**: 单日涨 3607 star，直接原因是 Cloudflare 博客公开了内部'漏洞挖掘 harness'，同时把这个源头技能开源；加上 skills.sh 这类 Agent 技能生态刚起量，大家想装一个官方出品的审计技能试试。

### [alibaba/open-code-review](https://github.com/alibaba/open-code-review)

 `Go` ⭐ +3,286 今日新增 · 35,315 总星数

> 阿里开源的 AI 代码审查 CLI：确定性工程管线管流程，LLM Agent 管判断，输出精确到行的评论，主打高精度、低 token。

**亮点**

- 精度换召回是明确取舍：和 Claude Code 用同一个底层模型比，F1 和 Precision 更高，token 只花约 1/9，但 Recall 更低——宁可少报，也不报一堆假问题让人挨个 triage。
- 自建了 AACR-Bench 并开源到 HuggingFace：50 个热门开源仓库、200 个真实 PR、10 种语言，1505 条由 80 多位资深工程师交叉标注的 ground truth，不是自己拍脑袋的评测。

**核心功能**

- 混合架构分工明确：审哪些文件、文件怎么分组、每个文件套哪条规则，全由工程代码定死；只有取上下文和做判断交给 LLM Agent。比如 message_en.properties 和 message_zh.properties 会被打包成一个审查单元，各跑一个子 Agent、上下文互相隔离，顺带支持并发。
- 内置多语言规则集，覆盖空指针、线程安全、XSS、SQL 注入这些老毛病。规则匹配走 Go 模板引擎按文件特征命中，而不是塞进提示词让模型自己记，稳定性更好、噪音更少。
- 评论定位和评论反思是独立模块：一条评论该落在哪一行、该不该发出去，都要再过一遍校验，专门治通用 Agent 行号漂移、文件引用对不上的毛病。
- 支持 ocr scan 整文件扫描，没有 diff 的老代码也能审，用来看不熟的仓库。模型端兼容 OpenAI 和 Anthropic 接口，也能挂到 Claude Code、Codex、Cursor、Kimi Code 上跑。

**适用场景**: 研发团队把 ocr 挂进 CI 或 PR 流程做自动初审，先挡掉空指针、注入这类低级缺陷，减少人工评审的体力活；接手历史仓库的工程师用 ocr scan 整目录扫一遍，快速摸清代码里埋的雷。

**竞品对比**: 对手是 Claude Code、Cursor 这类通用 Agent 做审查，以及 CodeRabbit、Qodo 这类商业 SaaS。最大差别是它不靠自然语言 Skill 驱动，文件选择、分组、规则匹配这些环节是硬编码流程，所以在很大的 changeset 上不容易偷懒漏文件。

**成熟度**: 阿里内部跑了两年、几万开发者用过，OpenSSF Gold 认证，npm 上有正式包；但开源版本刚放出，外部生产案例还少，接口可能还会动。

**趋势信号**: 阿里把内部用了两年的代码审查助手开源，正好撞上今年各家都在拿 Agent 做 code review、又普遍嫌通用 Agent 又贵又吵的节点，今天单日涨 3286 星。

### [Tencent/BrowserSkill](https://github.com/Tencent/BrowserSkill)

 `TypeScript` ⭐ +1,302 今日新增 · 4,438 总星数

> 腾讯开源的工具：AI Agent 通过 bsk CLI 加浏览器插件，接管你已登录的真实浏览器干活，你还能同时用自己的浏览器。

**亮点**

- "借标签页 + 归还"的显式协议加上独立 Agent Window，是被"不打扰用户"这个产品约束倒逼出来的架构选择。绝大多数同类工具直接另起一个浏览器实例，代价是登录态全丢。
- 只暴露一个 shell CLI，不绑 MCP 也不绑具体模型，把兼容面最大化；同时用内容哈希管理 skill 版本，避免自动更新冲掉用户自己改的指令。

**核心功能**

- 本地 daemon + 浏览器插件的架构：Agent 必须显式"借"你已经打开并登录的标签页，任务结束归还，其他标签页不碰，所以直接复用真实 cookie 和登录态，不用另建 profile 或测试账号。
- Agent 任务跑在独立的可见 Agent Window 里，和你自己的窗口物理隔开，因此可以边让 Agent 操作网页边自己继续上网。
- human-in-loop 是内置的：碰到验证码、登录、二次确认弹窗时，Agent 把控制权交回给你，你处理完它接着跑。
- Agent 无关的接入方式：只要 Agent 能调 shell 就能用 bsk，bsk install-skill 可往 Cursor、Claude Code、Codex、OpenClaw 等 8 种以上 harness 写 skill，并用内容哈希做基线——本地改过就暂停自动更新，不覆盖你的定制。

**适用场景**: ['让 Agent 操作已有登录账号的网页：在已登录的后台拉数据、填表、跑 Web 应用的端到端流程。用户是写 Agent 工作流的开发者、做数据采集或 QA 的人，他们不想再申请测试账号、也不想每次手动过二步验证。', '沙箱里跑 Agent 的场景：用 BSK_HOME 加 BSK_AUTO_START=0 把 daemon 留在宿主机，容器里只发命令。']

**竞品对比**: 对标 Playwright MCP、Chrome DevTools MCP、browser-use、Stagehand。最大差异：那些方案要么另起浏览器实例、要么通过 MCP 绑死客户端，登录态和"你同时在用浏览器"这两件事都处理不好；BrowserSkill 直接复用你当前的浏览器，并用 CLI 做到 Agent 无关。

**成熟度**: 工程化程度不低（已上架 Chrome Web Store 和 Edge 加载项、三平台安装脚本、doctor 自检、skill 版本管理），但 Firefox 还只是计划中，刚开源就爆量的早期项目，CLI 细节可能还会变。

**趋势信号**: 让 Agent 上网是当前最热的方向，而真实登录态和验证码是公认最难绕的坎；腾讯出品加"把一行命令丢给你的 Agent 就装好"的引导方式，直接吃到了 Agent 生态扩散的流量。

> ECC 是一个给 AI 编码代理（Claude Code、Codex、Cursor 等）做统一增强的开源层，提供技能、记忆、安全审查和研究优先的工作流，让同一套配置在 7 种 agent 工具里通用。

**成熟度**: 工程化程度不低（npm 包、GitHub App、付费订阅、多语言文档齐全），但核心仍是配置和提示词层，API 稳定性待观察；另外 26 万星标与项目体量明显不匹配，可能刷量，别只看这个数字判断成熟度。

**趋势信号**: Claude Code、Codex、Cursor 等 agent 编码工具在 2025-2026 年集中爆发，各家配置格式和记忆机制互不兼容，社区正缺一个跨工具的技能、记忆和权限统一层，ECC 踩在这个缺口上。

### [alphaXiv/OpenResearch](https://github.com/alphaXiv/OpenResearch)

 `Rust` ⭐ +939 今日新增 · 5,066 总星数

> OpenResearch 是本地优先的研究工作台，把 Claude Code、Codex 等编程 Agent 变成研究 Agent：能查文献、提假设、改代码、跑实验。每个研究方向用独立 git worktree 隔离，实验结果可追溯、可复现。

**亮点**

- 不自己造 agent，而是套在现成 coding agent 外面加一层实验编排——这层做的是并行隔离、证据归档和运行环境适配，恰好是裸 agent 缺的部分。
- autoresearch 闭环：提想法、改代码、起实验、看证据、定下一步能全自动跑，多个 agent 走不同方向，实验树保留各自血缘。

**核心功能**

- 并行探索用 git worktree 做隔离单位：每个研究方向开一个独立 agent 会话 + 独立 worktree，多个 agent 同时改代码互不冲突，比开容器/复制目录便宜。
- git-native 实验树：每次 run 都对应一个不可变的 commit 快照归档，实验是变体树上的节点，能顺着谱系回溯哪次改了什么、结果如何。
- 同一份提交快照可跑在本地、SSH、Slurm、Kubernetes、Ray、Modal、Hugging Face Jobs、Tinker 上，不需要先把仓库推到远端。
- 本地跑在 127.0.0.1:4791，数据存本地 SQLite；agent 框架和模型按会话选（Claude Code / Codex / OpenCode / Cursor，也可接 Ollama、LM Studio、oMLX 本地模型）。

**适用场景**: 做 ML 或系统研究的研究员、PhD、算法工程师，需要长期跑大量对照实验且要求结果可复现；也包括想把"读文献→写代码→跑实验→看结果→决定下一步"整条链路交给 agent 自动转的人。

**竞品对比**: 同领域有 Sakana AI 的 AI Scientist（端到端自动写论文）、OpenHands、SWE-agent 这类自动编码/自动科研 agent。最大差异：那些是自己实现 agent 循环，OpenResearch 复用 Claude Code/Codex/Cursor 当执行器，重点放在 git worktree 并行隔离和实验快照归档上。

**成熟度**: 项目很新，5k 星但 Windows 仍是 beta、远程服务无应用层鉴权、CLI 命令还在快速变化，属于早期可用、接口可能变动。

**趋势信号**: 编程 Agent 改代码已经成熟，社区正把这套能力往"自动跑科研"上接；加上作者 alphaXiv 在 arXiv 论文讨论圈本身有名，发布后直接冲到 GitHub Trending 日榜第一。

### [NationalSecurityAgency/ghidra](https://github.com/NationalSecurityAgency/ghidra)

 `Java` ⭐ +912 今日新增 · 78,617 总星数

> 美国国安局开源的反汇编/反编译框架，能分析 Windows、Linux、macOS 及各类固件二进制。免费替代 IDA Pro，靠 SLEIGH 描述语言低成本支持新指令集，最近因升级到 JDK 25 和 PyGhidra 直接跑 Python 再次冲上热榜。

**亮点**

- 核心思路是把"指令集支持"和"分析能力"解耦：p-code 做中间层，SLEIGH 做前端描述，所以加新架构是写配置文件而不是改编译器代码，这是它能开源覆盖这么多 CPU 的根本原因
- 带 Ghidra Server 做多人协同逆向，对同一个反汇编项目检出/检入，类似 Git 但管的是二进制数据库——商业竞品这块基本缺失

### [Hacker News · How Uber Protects Against Retry Storms](https://www.uber.com/us/en/blog/protecting-against-retry-storms/)

`RSS: Hacker News`

> Uber 复盘怎么防重试风暴：下游一变慢，客户端疯狂重试会把流量成倍放大，把局部抖动拖成整个系统雪崩。

**亮点**

- 思路上的转变：重试从「每个业务代码自己写自己的退避逻辑」变成「客户端库/服务网格层统一发牌照」，覆盖全公司海量服务，不用每个团队各修一遍。
- 重试不是越多越稳，而是一种要限额的稀缺资源。文章把重试当成需要配额管理的流量，而不是容错手段。

**核心功能**

- 重试预算（retry budget）：不再让每个调用点自己决定重试几次，而是全服务共享一份重试额度，通常只放行总请求量的很小一部分（业界常见 10%），额度用完就直接失败返回，不再往下游加压。
- 指数退避 + 抖动（jitter）：重试间隔随机化，避免几千个客户端在同一毫秒齐步重试，制造出人造尖峰。
- 超时预算/截止时间传递（deadline propagation）：给整条调用链一个总时限，剩余时间不够就放弃重试，防止下游已经超时了客户端还在补刀。

**适用场景**: 微服务后端和 SRE 团队。典型场景是网关、订单、支付这类强依赖下游的服务——某个数据库或第三方 API 开始变慢时，客户端 SDK 里几行重试代码就能把慢变成挂。

**竞品对比**: 同类思路早有：AWS Builders' Library 的 retry token bucket、Google SRE 书里的 retry budget、gRPC 内置的 retry throttling 都是这一套。Uber 的差异在于把它落到自家客户端库和通信框架里，规模上是全公司统一执行，而不是单服务自己配。

**成熟度**: 是一篇大厂生产经验博客，不是开源项目、没有版本号，方法在 Uber 自己规模上验证过，但文章未必给出可直接照抄的实现细节。

**趋势信号**: 「亚稳态故障」（metastable failure，系统被一次小抖动推进去就自己爬不出来）这两年在大厂事故复盘里被反复点名，AWS 和 Google SRE 都专门科普过，所以这类「大厂怎么扛住级联故障」的经验贴一直有人看；不过这条 HN 只有 70 分 30 评论，热度算中等。

### [dev.to · How OpenHiggsfield Scaled Next.js Server Actions: Request Coalescing, 38 AI Models, and Zero Queue Locks](https://dev.to/niraj_matere/nextjs-server-action-serialization-high-throughput-request-coalescing-declarative-multi-model-1mg6)

`RSS: dev.to`

> 开源多模型 AI 生成工作台 open-higgsfield，用客户端批量轮询绕开 Next.js Server Action 逐个串行的排队卡死问题，并统一 38 个模型的参数接口。

**亮点**

- 单飞合并（single-flight）+ fan-out：一个定时器 tick 只对应一次 Server Action，任务数从 1 涨到 N，网络往返次数不变。
- 把并发问题的解法放在客户端而不是服务端——因为瓶颈本来就是 Next.js 的 per-client 串行语义，后端其实是空闲的，扩容后端没用。

**核心功能**

- 客户端合并轮询：把所有在跑的任务 ID 收进一个 Map<string, Waiter>，每 4 秒只发一次批量 Server Action，而不是每个任务各挂一个 setInterval。Next.js 对同一客户端的 Server Action 是串行执行的，各发各的会让新提交的 Action 排在队尾、UI 直接卡住。
- 服务端一次 Action 内用 Promise.all 并发调各家 provider 的 status 接口（Kling、Seedance、Flux、Minimax 等），把 N 个任务的等待压成一次往返，Node fetch 并发跑。
- 等待的 Promise 跨轮询 tick 一直挂着不 resolve，只有拿到 completed/failed/nsfw/canceled 四个终态才结束；10 分钟超时，连续 3 次查不到状态就放弃，避免任务泄漏。
- 声明式多模型目录层：把 38 个模型的参数 schema 抽成一份声明式配置，用它统一做参数校验和请求路由，加新模型只改配置不改业务代码（这部分文章中论证较浅）。

**适用场景**: 做 AI 视频/图片生成产品的团队，前端用 Next.js App Router、后端接多家模型厂商 API。典型场景是一个用户在页面上同时提交好几个生成任务，还要能随时改参数、点提交，不希望被后台轮询拖卡。

**竞品对比**: 常见的替代是 SSE/WebSocket 长连接，或者 react-query/SWR 轮询。前两者要额外维护实时通道，后者每个 query 独立发起，撞上 Server Action 串行一样排队。open-higgsfield 的差异是只用批量 Action 就绕开串行，不引入长连接服务。

**成熟度**: 早期项目，来自一篇 dev.to 技术拆解文章，仓库版本和 issue 响应情况文中未提及，API 大概率还会变。

**趋势信号**: Next.js App Router Server Action 的 per-client 串行语义最近在生产环境被反复踩坑讨论，同时 AI 生成产品又普遍要同时接好几家模型厂商，这两个痛点撞在一起让这篇拆解火了。

- 把 ERP 相关责任拆成四类：厂商管标准产品和文档化 API，实施商管合同内的交付缺陷，企业自己管业务规则（哪个事件生成财务记录、哪个例外要审批），最后必须有人管集成的自定义代码、连接器配置、监控、重试路径和凭据——四类不能混为一谈
- 给出五个问题当交接验收标准：什么触发集成、哪个系统哪个字段是唯一数据源、怎么发现跑失败、人在哪里能安全续跑或修数、API 或审批规则变了谁来改；答案只存在某个人脑子里就算没交接完
- 诊断方法是从一个有人工修补痕迹的流程入手，把记录从业务事件一路追到财务/管理报表输出，标出数据离开系统的点、人工介入的点、变化最频繁的点，最后产出五选一的决策清单（改配置、澄清业务规则、用厂商支持的连接器、补一小层、指定维护人），而不是列一堆新功能需求

**适用场景**: 新加坡中小制造企业的 IT 负责人、财务主管和 ERP 项目经理。典型场景：实施商做完项目撤场后，ERP 与仓库、供应商门户、CRM、生产文件之间的对接出问题，没人能回答失败原因，只能靠人手工对账修补。

**竞品对比**: 同类话题通常由 iPaaS 厂商（Workato、Boomi、MuleSoft）或 ERP 厂商撰写，落点基本是'买我们的连接器/平台'。这篇引用 Workato 的《ERP Integration Singapore (2026)》，但立场偏向独立集成商，主张先诊断边界再决定，不推整套平台替换。

**成熟度**: 不是代码仓库，是一篇实践观点文章，附 Omni Care 的官网博客引流链接（UTM 标记齐全），无数据、无案例细节，属经验总结类内容，可作交接清单参考，不宜当权威标准。

**趋势信号**: 文中引用的 Workato 资料标注到 2026 年，说明 ERP 与 iPaaS 集成在新加坡 SME 市场是当下热题；同时实施商交付完就撤、企业自己接手烂摊子已是普遍现象，独立集成运维这块需求正在被单独拎出来做成一门生意。

### [dev.to · I got tired of babysitting coding agents](https://dev.to/brasthapp/i-got-tired-of-babysitting-coding-agents-jen)

`RSS: dev.to`

> Rig 是跑在多个编码 Agent 之间的编排层：父 Agent 拆任务、划定文件范围，Worker 走 MCP 执行，父 Agent 跑真实验证后才算完成。

**亮点**

- 把「exit 0 不等于验收」当成产品核心：父 Agent 定义验收点并自己重新跑检查，只有它能把任务标成 verified，子 Agent 无权宣布完成
- 不做 Agent 本体，只做控制面：同一套 harness 可以混搭不同厂商的 CLI，父用 Codex、子用 Grok 都行，这也绕开了单一厂商 subagent 只能在同一生态内嵌套的限制

**核心功能**

- 父 Agent 不把聊天记录丢给子 Agent，而是产出结构化 brief（改什么 / 不改什么 / 验收标准），并按路径锁定文件所有权，避免多个 Agent 改到同一个文件
- 子 Agent 通过 MCP（模型与外部工具的标准调用协议）以工具调用和任务状态交接，不靠终端间复制粘贴；任务和文件归属落在仓库的 .rig/ 目录里，不散在聊天记录中
- adaptive 模式下父 Agent 维护一个 DAG（有向无环图），只有在文件和资源范围不重叠时才并行；子 Agent 不能再生成子 Agent，默认最多 12 个节点

**适用场景**: 适合已经在 Codex、Claude Code、Cursor、Grok 之间来回切换、并且试过并行开多个 Agent 的开发者。典型场景是让 Agent 改一批测试或重构模块，合到 main 之前需要确定性的检查结果，而不是只看它自己说测试过了。

**竞品对比**: 对比 Claude Code 的 subagent、Codex 的多 Agent 模式、以及 Conductor 这类并行 Agent 工具，Rig 最大差别是跨厂商 + 强制验收 + 按文件不重叠构建 DAG。前者通常绑定自家模型，且子 Agent 只回报结果，父 Agent 不一定重跑检查。

**成熟度**: 早期个人项目，curl | bash 安装，配置写在 .rig/harness.toml，尚未见版本号和社区验证，API 与配置格式可能变动。

**趋势信号**: 2025 年编码 Agent 泛滥，MCP 刚成为事实标准，社区正集中吐槽「Agent 说完成了但 diff 不能合」，多 Agent 编排成了当下最热的补位方向。

## 趋势观察

今天这批项目，几乎都在干同一件事：给 AI 编程 Agent 补流程、补纪律。

以前是问一句答一句，现在流行把资深工程师的做法写成 markdown 技能包，塞进 Claude Code、Cursor 等各家 Agent，让它按 spec、测试、评审的顺序干活。阿里、Cloudflare、Anthropic 都在出这类东西。编排层也冒出来了：父 Agent 拆任务、划文件范围，Worker 走 MCP 执行，父 Agent 跑真实验证才算完成。

第二个共同点是本地优先和自托管。语音工作室、知识库、多智能体助手，都强调数据不出自己机器。模型也尽量不绑厂商，一套配置想在七种工具里通用。

第三，推理往消费级硬件挤。纯 C 写的 MoE 引擎把显存、内存、SSD 当一层用，744B 模型想在家用机上跑起来。

安全也在变热。NSA 开源的反汇编框架冲上热榜，Agent 被派去定时扫仓库、提修复 PR，从被动问答变成后台巡检。

一句话：Agent 不再比谁更聪明，而是比谁更守规矩、更省钱、更能留在你自己手里。
