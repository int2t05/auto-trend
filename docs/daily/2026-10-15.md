### [morluto/rea](https://github.com/morluto/rea)

 `TypeScript` ⭐ +41,034 今日新增 · 248,215 总星数

> 把 Ghidra/IDA 等逆向引擎和 JS、.NET 分析封装成 MCP，让 AI Agent 直接拆解本地 app 并复刻功能。

**亮点**

- 从网页一路钻到原生二进制是同一套工作流：网站 → JS/Electron → .NET 程序集 → 原生二进制，Agent 能顺着调用链逐层下钻，不用每换一层目标就换一个工具
- 不重造反编译器，直接复用用户已装的 Hopper/Ghidra/IDA；setup 时按 agent 逐个改写 MCP 配置，并给原配置留备份

**核心功能**

- 用 MCP 协议把逆向能力接给 Agent：本地起 MCP server，把 Hopper/Ghidra/IDA 的伪代码、汇编、字符串、符号表和交叉引用包装成可调用工具，Agent 不用自己写 IDAPython 脚本去驱动那些 GUI
- 静态 JS/Electron 分析不依赖任何反编译引擎：直接吃解包后的 JS 目录或 ASAR 包，输出模块列表、import 关系、Electron 主进程/渲染进程边界，纯静态解析
- 每个结论都带 evidence 和 limitation：返回代码片段、引用出处，以及哪些地方没查清，Agent 拿证据继续追问或写实现，而不是给个黑盒答案

**适用场景**: 产品经理或独立开发者看到竞品某个功能想抄实现时，让 Claude Code、Cursor 通过 REA 去拆本地安装的桌面 app 或 Electron 包，先看懂逻辑再写自己那版；安全研究员和固件分析人员则用它让 Agent 批量跑二进制伪代码和调用关系。

**竞品对比**: 和 GhidraMCP、ida-pro-mcp、Binary Ninja 的 MCP 插件比，那些基本绑死单一引擎、单一目标；REA 把多个逆向引擎和 JS/Electron/.NET/Web 统一成一个 MCP 工具目录，且 CLI 与 Agent 走同一套流程，JADX 之类只反编译不做 Agent 编排。

**成熟度**: MIT 协议、npm 上持续高频发版、README 有 21 种语言，但明说接口变化快、要常更新，仍属早期快速迭代项目，版本未到 1.0，生产环境需锁版本。

**趋势信号**: 踩中 MCP 生态爆发加 coding agent 普及这一波，把原本只在安全圈本地跑的逆向工具接进 Agent 工具链；不过 24.8 万星、单日 4.1 万星明显不符合真实增长曲线，热度数字要打折看。

### [ifixai-ai/iFixAi](https://github.com/ifixai-ai/iFixAi)

 `Python` ⭐ +2,109 今日新增 · 27,663 总星数

> iFixAi 是一个 AI Agent 审计工具：检查 Agent 有没有按业务 KPI 和组织权限办事，而不只看延迟和 token。默认跑 10 项检查、约 120 秒出评分，支持 CLI 和 Claude Code/Codex 插件。

**亮点**

- 评测目标换了：常规 eval 看 token 效率、延迟、提示注入，iFixAi 看的是业务对齐和越权。README 举的例子是客服 Agent 隐藏欺诈标记、付了经理已驳回的退款、改了收款账号，而常规 eval 全部显示绿灯。
- 评分权交给外部评委：允许把打分交给独立第三方或多评委 ensemble，这在 Agent 审计里是个明确的信任设计取舍，代价是多一层集成复杂度。

**核心功能**

- 把审计拆成 60 个检查项（inspection），按 smoke/strategic/essential/core/extended 分套件。默认只跑 10 项，--full-run 跑全量，适合从快速冒烟到审计留档的不同深度。
- 评分者可选：自己评、指定一个独立厂商评、或多个评委组成 ensemble 评。目的是避免 Agent 开发者既当运动员又当裁判。
- 支持审计已记录的动作轨迹（trajectory assurance）：拿 Agent 真实跑过的操作日志回放检查，而不是只跑合成测试用例。
- 三种驱动方式跑同一套诊断：CLI 向导（配置落到 ifixai.yaml，密钥只写环境变量名不写明文）、显式 flag（给 CI 用）、以及 Claude Code / Codex 插件让 Agent 自己给自己做审计。

**适用场景**: 适合上线客服、退款、支付、风控这类有权限边界的 Agent 的团队，以及合规和平台工程角色。典型用法是上生产前跑一遍，或接进 CI 定期跑。

**竞品对比**: 同领域有 promptfoo、DeepEval（LLM 测试框架）、NVIDIA garak（红队扫描）、Langfuse/LangSmith（可观测性）。差别在于这些工具多数按技术指标打分，iFixAi 声称按业务 KPI 和组织架构打分，并且允许换评委方。

**成熟度**: 有 PyPI 包、Apache 2.0 许可、CI 和多语言文档，看起来是正式项目，但仓库很新、缺少版本号和 issue 响应的公开信息，建议按早期项目对待，API 可能变动。

**趋势信号**: Agent 开始真正接手退款、支付这类有权限的操作，企业需要能对监管和内部风控交代的审计结论；项目方同时在 Product Hunt 拿到日榜第一、Trendshift 拿 Python 周榜第一，流量被放大。

### [xtool-org/xtool](https://github.com/xtool-org/xtool)

 `Swift` ⭐ +1,502 今日新增 · 11,055 总星数

> 用 SwiftPM 在 Linux/Windows/macOS 上把纯 Swift 代码编译打包成 iOS 应用，签名后装进真机，全程不用 Xcode。解决的是「非 Mac 环境做不了 iOS 开发」这个老问题。

**亮点**

- 把 Apple Developer Services（证书、App ID、描述文件申请）做成命令行子命令和 XKit 库里可直接调用的 API，等于用 Swift 重写了一遍 fastlane 的 cert / sigh。
- 项目里没有 .xcodeproj，唯一真相是 Package.swift，整个 iOS 构建流程挂到 SwiftPM 的命令和插件上，而不是去解析 Xcode 的工程文件。

**核心功能**

- 交叉编译自己做：用 swift.org 发布的 Darwin Swift SDK（一套能在非苹果系统上编出 iOS/macOS 二进制的工具链），把 SwiftPM 包直接编成 arm64 iOS 可执行文件，不调 Xcode 的 clang 和 SDK。
- 把 Xcode 独占的构建步骤重写了一遍：编译 Asset Catalog（图片资源目录）、storyboard/nib，生成 Info.plist 和 entitlements，最后拼成 .app 和 .ipa。
- 签名不用 codesign，改用 OpenSSL 生成 CMS/PKCS#7 签名块，按苹果格式嵌进二进制；设备通信走 usbmuxd，实现 install / launch / uninstall。

**适用场景**: 在 Linux 或 Windows 上写 Swift 的开发者，想顺手做个 iOS 客户端但手边没 Mac；以及 CI 里想跑 iOS 打包、又不想养 Mac 构建机的团队，比如在 GitHub Actions 的 Linux runner 上出 ipa。

**竞品对比**: 对标 Xcode 和 fastlane。fastlane 只管签名和上传，编译还是得回 Xcode；xtool 连编译和资源打包都自己做了。跟 Theos 这类越狱开发工具比，它走的是正规签名路线，能装到未越狱的真机。但它替代不了 Xcode 全部：没有 Interface Builder，也没有断点调试。

**成熟度**: 1.2.x 版本，编译、签名、装机这条主链路已经能跑通，但底层依赖苹果并未官方支持的交叉编译方式，踩坑了基本得自己啃；文档在 xtool.sh，社区规模还小。

**趋势信号**: Swift 官方开始发布 Darwin 平台的交叉编译 SDK，让「不用 Mac 也能写 iOS 应用」第一次真的可行，xtool 正好踩在这个时间点上。

**趋势信号**: 2025 年 AI Agent 从写代码扩散到安全攻防，自动化渗透成为热门方向，加上它支持本地 Ollama/vLLM 部署契合数据不出内网需求，今日涨星 1000+。

> Ghidra 是美国国家安全局开源的逆向工程框架，能反汇编、反编译并图形化分析各平台二进制文件。它免费替代 IDA Pro，还支持团队协作和脚本自动化，是恶意样本分析和漏洞挖掘的常用工具。

**成熟度**: 生产可用，NSA 内部长期使用后开源，版本已到 11.x，文档和社区都成熟，企业安全团队已大规模采用。

**趋势信号**: 近期版本把运行要求提到 JDK 25 并强化 PyGhidra（直接跑原生 CPython），降低 Python 用户上手门槛，因此重新冲到 trending；具体触发的热点事件我这边无法确认。

### [mksglu/context-mode](https://github.com/mksglu/context-mode)

 `TypeScript` ⭐ +947 今日新增 · 29,281 总星数

> 给 AI 编程助手做上下文窗口优化：工具输出扔进沙箱再回摘要（省 98%），会话记忆存 SQLite 用 FTS5 检索，跨 17 个客户端用 MCP + hooks 强制路由。

**亮点**

- 刻意不做「强制简短」：它只规定数据往哪走，不规定模型怎么写答案。README 引用了 kimi-k2.5 相关的 issue，说激进的简洁提示会拉低编码和推理 benchmark 分数。这个取舍和一堆「省 token 顺便帮你改写输出」的工具正好相反。
- MCP + 平台原生 hook 双轨：Claude Code 这类支持 hook 的平台，在 SessionStart 钩子里运行时注入路由指令，不往项目目录写任何文件；不支持的平台降级成一次性复制路由文件。

**核心功能**

- 工具输出沙箱：Playwright 快照 56KB、20 条 GitHub issue 59KB 这类原始数据不进上下文，由沙箱工具处理后再返回压缩结果，官方给的数字是 315KB 变 5.4KB。
- 「Think in Code」：不再让模型把 50 个文件读进上下文自己数，而是让模型写一段脚本去数，脚本里只 console.log 结果。它自己的例子是 47 次 Read（约 700KB）换成 1 次 ctx_execute（3.6KB）。
- 会话记忆落在 SQLite 里，记录文件编辑、git 操作、任务、报错；对话压缩后不整段回灌，而是建 FTS5 全文索引、用 BM25 按相关性取回。不加 --continue 就直接删掉上次会话数据。

**适用场景**: 长时间用 Claude Code、Cursor 这类 Agent 写代码的开发者：跑几十次工具调用后上下文被快照、日志、issue 列表塞满，30 分钟就烧掉 40% 窗口，需要它来兜住。 要在多个客户端（17 个平台）统一上下文策略的团队：有 hook 的走自动注入，没 hook 的复制一份路由文件。

**竞品对比**: 同类有 Claude Code 自带的 /compact、Cursor 的上下文管理，以及 Mem0 这类记忆层。最大差别是它把自己做成外挂 MCP server + hooks，不绑死某一个 IDE，而且检索走本地 SQLite + FTS5 + BM25，不依赖向量库或外部服务。

**成熟度**: 项目很新但热度极高，已上过 Hacker News #1（570+ 分）；注意 README 里微软、谷歌、Meta 那排企业 logo 只是徽章声明，没有公开案例佐证，许可证用的是 ELv2（限制拿去做托管服务），API 和平台适配都还可能变。

### [nvm-sh/nvm](https://github.com/nvm-sh/nvm)

 `Shell` ⭐ +52 今日新增 · 95,487 总星数

> nvm 是纯 shell 写的 Node 版本管理器，一条命令装/切多个 Node 版本且不动系统 Node；Node 24 转 LTS 带来的升级潮让它再上榜。

**亮点**

- 用 shell 函数而不是独立二进制是个被迫的设计：改 PATH 必须发生在当前 shell 进程里，子进程改不了父进程环境，所以 nvm 只能被 source 进去。这带来快切版本的能力，代价是要维护一堆 shell 配置文件和启动钩子。
- 版本目录隔离的思路：每装一个 Node 就是一份完整目录，切换只挪 PATH 指针，不需要重装也不需要清缓存；顺带把全局 npm 包也按版本隔离开，避免 A 项目依赖的 CLI 污染 B 项目。

**核心功能**

- 实现方式是一个 source 进 shell 的函数（nvm.sh），不是二进制程序。装完只改 PATH，让它指向 ~/.nvm/versions/node/vX.Y.Z/bin；每个 Node 版本一个独立目录，切换不重装、全局包也各自隔离。
- 靠 .nvmrc 做目录级版本锁定，再配合各 shell 的钩子自动切换：bash 用 PROMPT_COMMAND、zsh 用 chpwd、fish 用事件回调，进目录即切版本，不用手敲 nvm use。
- 工程细节做得细：Docker/CI 里用 BASH_ENV 让非交互 shell 也能加载 nvm；支持 NVM_NODEJS_ORG_MIRROR 走镜像源、支持离线安装；装新版本时用 --reinstall-packages-from 把全局包迁过去。
- 跨 shell 兼容到 POSIX 这一层，sh/dash/ksh/zsh/bash 都能跑，所以 Alpine 的 ash 环境也能用，代价是所有逻辑都得用 shell 写。

**适用场景**: 本机同时开多个项目的 Node 前后端开发者：老项目钉 Node 16/18、新项目要 Node 24，用 .nvmrc 进目录自动切版本。另一类是 CI 和 Docker 构建，在镜像里装指定 Node 版本跑测试或发 npm 包。

**竞品对比**: 主要竞品是 fnm（Rust 写的单二进制）和 Volta（按 package.json 自动切版本、团队可锁定），以及多语言通吃的 mise/asdf。最大差异：nvm 零依赖、纯 shell，安装脚本和文档到处都是，是事实标准；但每次开 shell 都要 source 一段脚本，启动比 fnm/Volta 慢，也没有按 package.json 自动切换的内置能力。

**成熟度**: 生产可用：超过 15 年历史、95k star，Docker 官方 Node 镜像和大量 CI 模板默认用它；版本号虽仍是 0.40.x（未到 1.0），但命令行为早已稳定。

**趋势信号**: Node 24 转入 LTS、Node 18 停止维护，团队集中升级 Node 大版本，版本切换工具被频繁用到；这是长青项目周期性回榜，不是新功能驱动。
