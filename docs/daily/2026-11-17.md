### [kajisho5/ffmpeg-skill](https://github.com/kajisho5/ffmpeg-skill)

 `Python` ⭐ +367 今日新增 · 7,252 总星数

> 给 Claude Code、Cursor、Codex 这类编码 Agent 装一个本地视频剪辑器：42 个 FFmpeg 工具加 MCP 服务，剪片、加字幕、改画幅、调响度、按平台导出，全在本机跑，不要云、不要 API key。

**亮点**

- 把"Agent 会瞎猜 FFmpeg 参数"这个真问题当设计前提：教固定工作流 + 强制校验产物，而不是再包一层 ffmpeg-python 风格的 API
- 仓库定位克制，只当"手"不当"脑"——不决定剪哪里、不管字幕文案对不对（照用户给的原文烧，不擅自改写），判断留给上层 Agent

**核心功能**

- 工具的 input_schema（MCP 工具定义里参数那部分）不手写，运行时直接从同一个 argparse parser 生成，CI 检测到不一致就构建失败，防止 CLI 和 Agent 看到的接口各说各话
- 走的是 probe → 尽量无损剪切（stream copy 不重编码）→ check 测量成片 → verify 的固定流程，Agent 不能只喊"做完了"，必须打开结果文件量时长、分辨率、帧率
- 42 个工具都既能在命令行用又能当 MCP 工具调，但 tools/list 默认只暴露核心 12 个，避免把客户端上下文塞满，设 FFMPEG_SKILL_MCP_FULL=1 才列全部
- 纯 Python 标准库实现，只依赖系统上的 ffmpeg 和 ffprobe，CI 里跑 FFmpeg 6.1/7.1/8/9 四个版本

**适用场景**: 用 Claude Code 或 Cursor 做内容的开发者、剪辑辅助人员：手上有一段录屏或访谈，想让 Agent 直接切掉静音段、压到 9:16、烧上字幕、导成抖音/B 站规格，但素材涉密不想传云 已有视频流水线的团队：把它的 probe.py、silence.py、scenes.py、check.py 当作底层执行层，接在自己的调度或 Remotion 动效工程下面

**竞品对比**: 对比裸 FFmpeg 命令和 ffmpeg-python、MoviePy 这类库，它多的是 Agent 可读的机器契约和成片自检；对比各类 ffmpeg-mcp 服务，最大差别是 schema 由 argparse 派生加 CI 防漂移，以及输出会被实际测量而不是只返回成功码

**成熟度**: 版本已到 v3，npm 有包、有 CI 和 OpenSSF Scorecard、每个功能都有可复现的前后对比 demo，但基本是单人维护，生态里其他仓库都指向它，算可用但别指望有人兜底。

**趋势信号**: Agent Skill 和 MCP 成了 Claude Code、Cursor 之后的新包装格式，大家正把本地 CLI 能力一个个改造成 Agent 能直接调的工具，这个项目踩在这个转换点上。

### [google-research/paper-orchestra](https://github.com/google-research/paper-orchestra)

 `Python` ⭐ +313 今日新增 · 1,881 总星数

> Google Cloud AI Research 开源的多智能体流水线，把想法和实验日志自动写成带文献综述、图表和会议 LaTeX 模板的论文初稿。

**亮点**

- 把「写完再自我批评」拆成两个不同模型来跑：writer agent 产出内容，reflection agent 单独评审改写，避免同一个模型自说自话式自检
- 产物直接是能编译的 LaTeX 而非 Markdown，模板按会议目录组织，这是它和多数「AI 写作助手」最实质的区别

**核心功能**

- 五个专职 agent 串成流水线：大纲 → 文献综述 → 分节写作 → 反思改写 → 画图；写作模型和反思模型是两个可分别指定的 LLM（比如 Gemini 写、GPT 挑毛病）
- 接 Semantic Scholar API 做文献检索，先排序筛选再按章节融入引用，不是让模型凭记忆编参考文献
- 画图 agent 自己写代码从实验日志生成图表，最终按 templates/ 下的会议模板（如 cvpr2025）编译出可直接提交的 LaTeX，换会议只换模板目录
- 仓库里还带 autoraters/ 目录，用自动评分脚本给生成论文打分，方便做对比实验

**适用场景**: 手里有 idea 和一堆实验日志、但写初稿最痛苦的研究生和科研团队；也适合搭建「自动科研」闭环的实验室，把它接在实验自动化后面当写作端。输入是你自己的原始材料目录，数据集官方暂未放出。

**竞品对比**: 同赛道有 Sakana AI 的 AI Scientist、Agent Laboratory 和 Stanford STORM。STORM 只做长文综述不写实验论文；AI Scientist 走「自动做实验 + 写论文」全流程但写作偏模板化；PaperOrchestra 只啃写作这一段，差异点在于文献检索 + 可编译会议 LaTeX + 代码生成图表三件事打包在一起。

**成熟度**: 早期研究代码，没有版本号，训练/评测数据集还没发布，README 明确写「非 Google 官方支持产品」，不建议直接拿去投稿。

**趋势信号**: AI Scientist 的论文通过 workshop 同行评审后，「AI 自动写论文」的争议正热，Google Cloud AI Research 的招牌加上这个敏感话题，一天涨 300 星。

### [DeanChensj/jiangshan-map](https://github.com/DeanChensj/jiangshan-map)

 `JavaScript` ⭐ +288 今日新增 · 7,342 总星数

> 把中国 2400 年历史做成可拖时间轴的交互地图，点任何古城就能看它历朝的名称和辖境变化，浏览器里直接查古地名对应今天哪儿。

**亮点**

- 真正的重活是数据：把谭其骧《中国历史地图集》那类纸质图录手工转成矢量多边形，还要给每个地名补齐跨朝代的行政沿革和事件，198 个快照的取舍和去重边界是主要成本
- 把「秋海棠→雄鸡」版图切换、1881 年收复伊犁、1898 年租借地这些敏感又复杂的节点做成时间轴上的独立阶段点正面呈现，而不是回避

**核心功能**

- 按 18 个历史时期切出 198 张疆域快照，每张是一套独立多边形图层；切换阶段时会用虚线叠出上一阶段的边界（项目里叫 Ghost Boundary Diff），一眼看出哪块地是新得的、哪块丢了
- 每个古地名都存了跨 18 朝的行政区划沿革（战国郡→汉州→唐道→宋路→元明清省→今市），点城市弹出这张沿革卡片并挂上发生在此地的具体事件（咸阳的商鞅变法、樊城的关羽水淹七军），而不是只在地图上戳个点
- 地图状态全部编码进 URL 查询参数（?year=1415&zoom=1.75&center=115.8,33.2&hover=Yingtian），任意年份、任意地点都能生成可直接分享的链接；纯静态前端，无后端，朗读用浏览器自带 SpeechSynthesis

**适用场景**: 读《资治通鉴》或古诗时想知道黄州、蓝关、朱仙镇今天在哪的人；中学历史老师备课、历史类短视频/公众号作者找配图和疆域对比图；写历史小说的人核对某年某地归谁管。

**竞品对比**: 对标的纸质版是谭其骧《中国历史地图集》，数字侧是复旦 CHGIS（偏研究、给的是数据和 GIS 图层，得用 QGIS 才能看）、全历史 App、OpenHistoricalMap；最大差异是这个开箱即用、免装、可深链分享，还额外挂了诗词路线和君主年号。

**成熟度**: 个人项目，未打版本号，边界线为示意精度、数据靠作者一人校订，能当科普和教学辅助，不适合当学术引用来源。

**趋势信号**: 作者写的复盘长文《从课本地图到 1k GitHub stars》在中文技术/历史社区传播，加上「中国历代疆域变迁」本身自带话题度，几天内从千星冲到七千。

### [mvanhorn/last30days-skill](https://github.com/mvanhorn/last30days-skill)

 `Python` ⭐ +135 今日新增 · 68,394 总星数

> 把 Reddit、X、YouTube、HN、Polymarket 等平台的近 30 天内容并行抓下来，按点赞数和真金白银的赔率排序，再由 AI 写成一份摘要，补上单家 AI 搜不全的空白。

**亮点**

- 思路是把十几个互相不通的封闭平台各开一个后门（用户自己的 key 或登录态），再让 Agent 从统一的地方并行调用、横向打分，而不是去做一个更好的搜索引擎；单家 AI 做不到，是因为各自只跟少数平台签了数据协议
- 用 Polymarket 的实时赔率当作事实性信号，压在相关新闻条目下面，同时标出赔率变动幅度。这个做法绕开了"谁说得响谁有理"，改成用下注的钱来表示相信程度

**核心功能**

- 自带密钥和浏览器登录态来打通各个封闭平台：Reddit、HN、Polymarket、GitHub 免密钥直接可用，X、YouTube、TikTok、LinkedIn 则在首次运行时由向导引导，配置 API key 或复用已登录的 cookie 会话
- 排序不用编辑权重，而用真实互动信号：Reddit 的 upvote、X 的 like、TikTok 的互动量、Polymarket 的下注赔率（谁掏钱谁说了算）、Digg Score，再交给一个 LLM judge 合并成一份带出处的简报
- 按 PATH 做可插拔探测：`arxiv-pp-cli`、`techmeme-pp-cli`、`yahoo-finance-pp-cli`、`digg-pp-cli` 只要在 PATH 上就自动启用对应数据源，没装就跳过，不会报错中断
- 本身是一份 SKILL.md 规格，不是独立应用：用 Claude Code 插件市场安装，或用 `npx skills add` 装到 Codex、Cursor、Copilot、Gemini CLI 等 50+ 个支持 Agent Skills 的宿主上

**适用场景**: 适合要在见客户、开会、做投资判断前快速摸清某个人或某家公司近况的人，比如销售、BD、投资人、记者；也适合追 AI 动态的开发者，用来替代 Google 搜不到的 Reddit 评论区和 X 热帖。

**竞品对比**: 对比 Perplexity、ChatGPT Search、Gemini：它们受授权限制，各自只能覆盖一部分平台（ChatGPT 有 Reddit 但没有 X，Gemini 有 YouTube 但没有 Reddit），本项目靠用户自带凭据把各家拼起来。对比 Exa、Tavily 这类搜索 API，差异是不做通用网页索引，只做"人对内容的反应"这一层。

**成熟度**: README 自称 v4 流水线，有多语言文档和 CI 校验，但核心采集依赖第三方接口和浏览器会话，平台一改版就容易挂；作为 skill 规格，命令行为还在快速变。

**趋势信号**: Agent Skills 生态正在扩张（Claude Code 插件市场、agentskills.io 等），这个项目正好是"跨平台数据 + 技能包"的样板，加上大家对 AI 搜索质量和 Google 结果的不满，被集中推到 Trending 第一。

### [sveltejs/svelte](https://github.com/sveltejs/svelte)

 `JavaScript` ⭐ +115 今日新增 · 89,127 总星数

> Svelte 是一个编译型前端框架：把组件在构建时编译成直接操作 DOM 的 JS，运行时不需要框架代码。现在因 Svelte 5 的 runes 响应式模型上线而重新受到关注。

**亮点**

- 把'框架'挪到构建期：产物是普通 JS 加细粒度 DOM 更新，代价是编译器要做更多分析工作（这也是它比运行时框架更难写的地方）
- Svelte 5 没有沿用 4 的'赋值即触发更新'魔术，改成显式 runes + 信号，解决了原来响应式在 .svelte 文件外失效、以及 store 语法分裂的问题

**核心功能**

- 编译期把组件编译成命令式 DOM 更新代码，运行时不带虚拟 DOM diff，框架本身的运行时体积接近零
- Svelte 5 引入 runes（$state/$derived/$effect），底层用信号（signal，一种记录依赖关系的细粒度响应式单元），更新时只重跑真正依赖该状态的代码，不再靠整体重渲染
- 编译器本身用 JavaScript + JSDoc 注释做类型检查（不用 TypeScript 编译步骤），配合 pnpm 构建，测试用 vitest 按 -g 过滤单个特性（如 transition）

**适用场景**: 前端团队做中小型 SPA、营销站、内容站点时用；配合 SvelteKit 做 SSR/路由。适合想要 Vue/React 的开发体验、但受不了运行时开销和大量样板代码的开发者。

**竞品对比**: 对比 React（运行时 + 虚拟 DOM + hooks）和 Vue（运行时 + 响应式代理），Svelte 的差异是把工作放在编译期，产物更小、更新路径更短；代价是生态和第三方组件数量明显不如 React，且编译器行为与框架版本强绑定。

**成熟度**: 生产可用：Svelte 5 已稳定、SvelteKit 1.x/2.x 有真实线上项目，文档完善、Discord 社区活跃，但 4→5 的写法不兼容，老项目需要迁移。

**趋势信号**: Svelte 5 的 runes 稳定后社区进入 4→5 迁移期，围绕 signals 模型与 SvelteKit 新版发布的讨论带动了星标增长。

**亮点**

- v3 用 Go 把前后端放进同一个二进制文件，不依赖外部数据库，备份和迁移时只要搬动一个文件；这对自托管场景来说是减少运维负担的关键取舍
- 把功能请求从 Issue 挪到 Discussions，让 Issue 区只留 Bug，项目维护者集中处理真正的问题，这也是项目从个人项目转向社区运营的信号

**核心功能**

- 后端用 Go 直接调用 Docker Engine API（通过挂载 /var/run/docker.sock），不套一层自己的 agent；前端编译进同一个二进制，部署只需一个容器，不需要额外跑数据库
- 内置 Crowdin 多语言流程，翻译文件由社区维护，不占用开发者的时间
- 发布 SBOM（软件物料清单，即列出镜像里每个依赖及版本），并用 Snyk 做漏洞扫描，方便企业做供应链审计

**适用场景**: 家里有 NAS 或小服务器、跑了一堆容器的个人用户，以及没有专职运维的小团队。他们用 Arcane 替代 Portainer，进行查看日志、重启容器、清理镜像这些日常操作。

**竞品对比**: 主要对手是 Portainer、Dockge 和 Yacht。Portainer 功能最全，但社区版限制节点数，且界面偏老；Dockge 只做 compose 文件管理，不管镜像和网络。Arcane 的差异在于它是 Go 单二进制、BSD-3 许可、没有节点数门槛，并且支持多语言。

**成熟度**: v3 还在 main 分支上开发，尚未稳定发布；2.x 是上一个稳定系列，说明 API 和界面可能还会变，适合尝鲜，不建议用在关键生产环境。

**趋势信号**: Portainer 社区版限制免费节点数、引导用户购买商业版，一批自托管用户正寻找替代品；Arcane v3 重写刚好在这个时间点推进，从而吸引了关注。

### [dream-num/univer](https://github.com/dream-num/univer)

 `TypeScript` ⭐ +1,828 今日新增 · 28,502 总星数

> Univer 是一个 TypeScript 写的前端 Office 引擎，提供表格和文档的编辑、公式计算、协同、文件导入导出能力，并以 SDK 形式嵌入你自己的产品或给 AI Agent 调用。现在受关注，是因为它把定位改成了“AI 办公底座”。

**亮点**

- 核心开源、服务端协同和导出、AI 扩展商业授权分开卖：Apache-2.0 拿到的是引擎和 API，实时协作、Office 文件高保真导入导出要走商业版，这条线划得很清楚。
- 内容模型和 Facade API（面向应用的封装接口）与 UI 解耦，同一套模型既能驱动可视化编辑器，也能在无界面场景跑计算，不用维护两份逻辑。

**核心功能**

- 插件化内核：表格、文档、公式、渲染都拆成独立插件，按依赖关系自动装载或卸载，想剪掉某个功能就直接不注册对应插件，打包体积和功能可以按需组合。
- 命令系统（Command）统一处理所有编辑操作：改一个单元格、插入一整行、批量格式化，都走同一条命令管线，所以跨功能的组合编辑和撤销/重做能对齐到同一份历史。
- 公式引擎带依赖关系跟踪，只重算受影响的单元格，而不是每次全表重算；同时内容模型和计算逻辑可以脱离编辑器运行，用在服务端做无界面（headless）的批处理计算和文件解析。

**竞品对比**: 和 CodeRabbit、Graphite Diamond 这类在 GitHub 上留评论的 PR 机器人不同，也和 Cursor / Copilot 那种在 IDE 里点“接受/拒绝”不同：它在本地浏览器做批注，反馈自动变成 agent 的下一轮输入，不用人再复制粘贴描述问题。

**成熟度**: 能日常用，已接 10 多个 agent、有官网文档和 TUI 配套；但 Inbox 是刚上线的新功能，迭代快，接口和交互可能还会变。

**趋势信号**: 多 agent 并行干活后，“人审批不过来”成了新瓶颈，Inbox 正好在这个时间点发布，从单次计划审阅扩展成多会话收件箱。

### [google-labs-code/stitch-skills](https://github.com/google-labs-code/stitch-skills)

 `TypeScript` ⭐ +529 今日新增 · 9,846 总星数

> Google Labs 把 Stitch（文字/图片转 UI 设计稿的 AI 工具）封装成一包 Agent Skills，让 Claude Code、Codex、Cursor、Gemini CLI 等编码 agent 直接调用 Stitch 生成、编辑、导出设计稿。

**亮点**

- 把 MCP 和 Skill 明确分工：MCP 只负责调远端 Stitch 服务，Skill 负责「先干什么后干什么」的流程和提示词，所以技能本身几乎不写业务代码，换 agent 时迁移成本极低
- 分发上用 sparse checkout 只拉需要的插件目录，配合 npx plugins / npx skills / Codex marketplace 三种安装方式，同时兼容各家的插件目录约定，OpenCode 这种不吃 marketplace 的还能手动拷目录

**核心功能**

- 能力分两层：Stitch MCP server 提供远端工具（生成屏幕、改屏幕、上传资源），仓库里的 skill 只是 Markdown 提示词+流程编排，所以同一份技能能跨 5、6 种 agent 复用，不用给每个工具重写一遍
- extract-static-html 把 localhost 上跑着的页面抓成自包含 HTML，CSS 和图片全部内联；code-to-design 再把它连同 DESIGN.md 一起传进 Stitch，实现「现有前端 → 设计稿」的反向迁移
- extract-design-md 扫描 /src 源码抽出设计令牌写成 .stitch/DESIGN.md，manage-design-system 再把它回灌到 Stitch 项目并批量套到所有屏幕上，形成代码→设计→代码的闭环
- react-components / react-native 把 Stitch 屏幕生成 React 组件或 StyleSheet 代码，带校验步骤和 token 一致性检查，不是一把梭生成完就完事

**适用场景**: 适合已经在用 Claude Code、Cursor、Codex 写前端的前端工程师和产品设计：手上有一套 React 老项目想快速出设计稿做改版，或者反过来拿到设计师的 Stitch 稿子想直接生成组件代码。也适合做 demo 视频的场景，remotion 技能能把设计稿导出成带转场的走查视频。

**竞品对比**: 对手是 Figma 的 MCP/Dev Mode、Vercel v0、Anima、Builder.io 这类设计↔代码工具。最大差异是它不绑定自家 agent，也不绑定自家 UI 框架，设计稿和代码两个方向都走；但代价是必须要有 Stitch 账号和 MCP server 才能跑，Figma MCP 那种本地文件级方案不依赖外部服务。

**成熟度**: 早期项目（Google Labs 实验性质，未到 1.0），文档齐全但技能之间有依赖，选择性安装容易缺件，且强依赖 Stitch MCP 这个外部服务。

**趋势信号**: Agent Skills 这个开放标准最近同时被 Claude Code、Codex、Cursor 采纳，加上 Google 发布 Gemini 3 和 Antigravity 编码 agent，Labs 顺势把 Stitch 打包成技能，正好赶上这波 agent 生态的窗口期。

## 趋势观察

今天的热榜指向同一个变化：Agent 正从演示品变成生产工具，围绕它的配套层在快速成型。一头是协议和标准。Agent 事件流协议冻结 1.0，多家框架接同一套前端；MCP、Skills 被做成可安装的包，浏览器、视频剪辑、Office、设计稿都能被 Agent 调用。另一头是验货和审稿。多 Agent 并行后，人审不过来，于是本地评审界面、技能体检、误报更低的代码审查流水线集中出现。大家不再只问“Agent 能不能做”，而是问“做得对不对、安不安全、省不省钱”。开发者生态也在变：Skills 像新的 npm 包，MCP 像新的 USB-C 接口，谁先把工具封装好，谁就占住 Agent 的入口。同时，自托管 Docker 面板、可拖时间轴的历史地图说明另一股需求没退：数据在自己手里，交互要直观。新闻热点表面是模型和 Agent，底层其实是工具标准化、质量把关和入口争夺。接下来比拼的不是 demo，而是谁能把 Agent 接进真实流程，还能让人放心签字。
