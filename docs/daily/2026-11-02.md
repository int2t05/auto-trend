### [pingdotgg/t3code](https://github.com/pingdotgg/t3code)

 `TypeScript` ⭐ +3,094 今日新增 · 38,671 总星数

> 把本机已登录的 Claude Code、Codex、Cursor 等命令行 Agent 统一接管，用手机、网页、桌面端远程驱动，复用你现有订阅，不用另买 API Key。

**亮点**

- 远程优先的架构取舍：会话状态和进程都留在本机 server，客户端只是壳，所以手机发起的任务和桌面看到的是同一条会话，不需要云端中转
- 作者明说不锁死方向，代码和构建链全开源（连 Vite+ 的 `vp` 工具链都写清楚），方向不对你可以直接 fork 出自己要的编辑器

**核心功能**

- 它自己不跑模型，只通过一层 provider 适配器驱动本机已装好的 CLI Agent（Claude Code、Codex、Cursor CLI、Grok Build、OpenCode、Antigravity、fx），抹平各家不同的登录方式和会话格式；Antigravity 走应用内 Google OAuth，其余靠 `xxx login` 的本地凭据
- 本机常驻一个 server（`t3 service install` 装成后台服务），Web、Electron、iOS、Android 都是薄客户端，手机连回家里那台机器就能接着跑任务
- 支持 MCP 双向连接：外面的 Claude Code、ChatGPT 等可以反过来接入它；每个 provider 支持挂多个账号切换；有权限模式控制工具调用是否放行

**适用场景**: 手里同时订了 Claude Max、ChatGPT Plus、Cursor 的开发者，想在手机上排队启动任务、通勤路上看进度、回家在桌面上接着改；也适合想用统一面板管理多个 Agent 会话的小团队。

**竞品对比**: 对标 Conductor、Codex 桌面应用、Claude Desktop、Cursor Glass。最大差别是它不绑定单一厂商，一个界面管七种 Agent，而且把手机远程当一等公民，还开源可 fork。

**成熟度**: 作者自标 very very early、明确说会有 bug、暂不接受大功能 PR，文档只有仓库里的 docs 目录还没站点，能日常用但功能会变。

**趋势信号**: 作者 Theo（t3.gg）自带大流量首发，正好撞上 Claude Code、Codex 各自把自己锁在官方客户端里的痛点——大家手上好几个 Agent 订阅，缺一个统一遥控器。

### [thedotmack/claude-mem](https://github.com/thedotmack/claude-mem)

 `TypeScript` ⭐ +1,526 今日新增 · 109,728 总星数

> 把 coding agent 每次会话里的工具调用轨迹压缩成结构化记忆，下次开新会话自动注入。解决的是每次重开 Claude Code 都要重新解释项目背景的问题。

**亮点**

- 记忆底座就是磁盘上的 markdown 文件，不是向量库。人和 agent 读同一份，出问题能直接 diff、能手动改，也不会被锁进某个黑盒服务
- 压缩跑在会话外：可以选官方 claude-mem observer、自备 OpenRouter/Gemini key、或直接烧 Anthropic 订阅额度，不占用主对话的上下文窗口

**核心功能**

- 挂在宿主的 hook 上抓每次工具调用（改文件、跑命令），会话结束后用 LLM 把原始轨迹压成带类型的观察条目，下次开会话时按相关性注入，不用人写 CLAUDE.md
- 记忆条目分 decision / bugfix / security_alert / sensitive 四类，只把这几类关键条目追加进按月滚动的 markdown 日志 memory/log/YYYY-MM.md，正文人眼可直接读
- 对没有 hook 的客户端（如 Grok Bot）降级成监听聊天日志文件落盘来取数据，另外暴露 MCP 搜索工具让 agent 自己回查历史

**适用场景**: 长期用一个仓库写代码的开发者，尤其是天天开新 Claude Code / Codex 会话、每次都要重新交代项目结构和历史决策的人；也适合想把「为什么这么改、修过什么 bug」沉淀成项目资产的团队。

**竞品对比**: 对比手写 CLAUDE.md / AGENTS.md，那是人维护、只存结论；对比 mem0、Letta\(MemGPT\) 这类通用 agent 记忆库，它们存的是对话。claude-mem 直接吃 coding agent 的工具调用轨迹，自动生成项目级记忆。

**成熟度**: 版本已到 15.8.2，安装器覆盖 Claude Code、OpenCode、T3 Code 等十多个宿主，文档有 30 多种语言；但迭代极快，托管记忆带 30 天试用转订阅，上生产前建议锁版本。

**趋势信号**: Claude Code、Codex、Gemini CLI 这类终端 agent 扎堆出现，「上下文窗口不够用」成了日常痛点，而多客户端之间又缺一层统一的记忆，它正好卡在这个位置上。

### [Renhuai123/ziwei-doushu](https://github.com/Renhuai123/ziwei-doushu)

 `TypeScript` ⭐ +941 今日新增 · 13,496 总星数

> 一个用 TypeScript 写的紫微斗数开源排盘引擎，包含排盘、四化、格局和古籍数据，另外发布 67.5 万张命盘、解压后 56.6GB 的解读数据集。它把倪海厦《天纪》的口传内容变成可查、可运行的数据。

**亮点**

- 把「解读」当数据集发布，而不只是提供代码：67.5 万张命盘 × 13 维度，按年份拆成 77 个文件，可以只下需要的年份，并附 SHA256 校验，等于把玄学内容做成像模型语料一样可下载、可复现的资产。
- 许可证按内容分层：代码用 MIT，解读数据用 CC BY 4.0（可商用），倪海厦讲课原话单独抽出来用 CC BY-NC-SA 4.0（非商用）。这种拆分避开了「开源代码并不代表开源讲课录音」的授权风险。
- 断语不是随手编的：每条引文要么能在《紫微斗数全书》原文里逐字找到，要么标出《天纪》第几集几分几秒可回放，查不到出处的直接删掉。

**核心功能**

- 排盘前先做真太阳时校正：用出生地经度差加均时差修正钟表时间，并内置 1986–1991 年中国夏令时起止表；遇到夏令时只做判定，从不自动扣除，并把换算做成可撤销的按钮，交给用户点击。
- 把时辰统一定义为地支序号 0–11，而不是 0–23 的钟点；农历转公历时，对闰月边界做 clamp，也就是把越界值压回有效区间；引擎会直接拒绝 2 月 30 日这类不存在的日期，避免脏数据进入排盘。
- 星曜亮度有多个流派配置，默认使用《斗数全书》，也保留「现代修正 v2」开关，并用 5 张金标准盘逐宫核对；解读数据集由引擎加断语库按确定性规则生成，不调用 AI，同一输入恒定得到同一输出，压缩后体积 161MB，靠 zstd 长窗口\(--long=27\) 把 56.6GB 压到这个大小。

**适用场景**: 适合做命理类 App 或小程序的开发者直接接入排盘；也适合研究传统术数、做 NLP 或知识库的人，把 877 万段结构化断语当成训练或检索语料。在需要批量生成命盘解读内容的内容运营场景也能用。

**竞品对比**: 最直接的竞品是 iztro 这类开源紫微排盘 JS 库。差异在于 iztro 主要提供排盘 API，而这个项目把真太阳时、夏令时、闰月和流派亮度这些容易出错的边界情况都包了进来，还额外提供体量很大的解读数据集，并绑定倪海厦体系的断语和引证出处。

**成熟度**: 处于早期阶段：文档写得很细，有 CI、线上站点和完整回归测试，但回归测试只有 5 条，引擎 API 在三个月内从 181 行扩到 641 行并有多次口径修正，接口仍可能变化。

**趋势信号**: 2026-10-15 发布 v4.0 解读数据集：命盘数增加 30%，解压后体积增加 71%，正文约 204 亿字，而且全部按倪师原话逐句校正。在「玄学 + 大模型语料」这个近期热度很高的方向里，它是一份能直接下载的真实结构化中文数据。

- 「先决策后执行」的网关设计：agent 拿不到直连工具的权限，必须绕回网关过一遍策略和审计才动手。代价是加一跳延迟，换来的是敢让它碰真实账号和文件
- coworker 是配置不是代码：examples/fintech/catalog/ 里放了 10 个现成角色（报销审核、会议纪要转待办、发布说明草稿、工单分诊等），复制一个目录进 agents/ 就多一个 bot

**核心功能**

- 每个 Bot 跑在独立容器里，自带 Chromium、自己的登录态和工作区，由 supervisor 拉起；一个 bot 的 cookie 和文件碰不到另一个
- 所有工具调用（电脑操作、文件、MCP server、UI 组件）都回打到同一个 gateway：先解析目标、按策略裁决、写一条 PostgreSQL 审计行，然后才真正执行；拒绝时直接点名违反了哪条规则
- Bot 只要是一个会说 AG-UI 的 endpoint 就能接进来，LangGraph、Mastra、CrewAI、Pydantic AI、Google ADK 或手写的都一样，治理挂在协议层而不是绑死某个框架
- Bot 的回答返回 CopilotKit 组件而不是纯文本，前端可以直接渲染成表单或卡片

**适用场景**: 适合要把 AI 助理放进自家机房的企业 IT/安全团队。比如财务用现成的 Risk Analyst 按政策核费用报销，客服拿它做工单分诊，HR 拿它答新员工手册问题——前提是每一步都能查是谁批的、为什么放行。

**竞品对比**: OpenHands、Browser Use、E2B 是给 agent 一台沙箱机器，但不管策略和审计；Dify、n8n 能编排流程却没有真浏览器和登录态。OpenAI/Anthropic 的 computer use 是托管闭源服务。OpenBot 的差异是自托管 + 一 bot 一容器 + 强制过审计网关。

**成熟度**: Beta 阶段，README 自己说是模板不是产品、有 rough edges、API 会动；跑起来要 Docker + Bun 1.4+ 和一份 CopilotKit Intelligence 授权。

**趋势信号**: CopilotKit 正用 AG-UI 协议铺 agent 生态，同时撞上今年企业对「能自托管、每步留痕」的 computer-use agent 的需求——ChatGPT 和 Claude 的 agent 能力越强，越多人问能不能跑自己机房。

### [kornia/kornia](https://github.com/kornia/kornia)

 `Python` ⭐ +101 今日新增 · 11,894 总星数

> Kornia 是一个跑在 PyTorch 上的可微分计算机视觉库，把滤波、几何变换、相机模型、RANSAC 求解器、特征匹配这些操作全做成可导、可批处理、可上 GPU 的算子。最近发布 0.9.x 并公布性能基准，热度上升。

**亮点**

- 项目定位从"算子更多的库"转成"可微分视觉与几何的参考实现和可执行规范"：写明约定、加一致性测试、公开诚实的基准，连自己输给 torchvision 和 OpenCV 的地方也列出来（eager 模式在重叠算子上比 torchvision 慢，OpenCV 赢在单图 uint8 CPU）
- 0.9.1 把 sigma 张量和 gamma/contrast/solarize 的取值校验放到设备上做，CUDA 调用（PyTorch ≥2.13 的 MPS 也是）不再需要回主机同步——这类细节通常没人管，但它直接决定训练吞吐
- 同时给 torch.compile 和 ONNX 导出兜底：1000+ 算子能导出 ONNX，每个算子的导出结果都有一张公开的支持表

**核心功能**

- 运算符支持逐样本参数：gaussian_blur2d 接收 \(B,2\) 的 sigma，warp_affine 接收 \(B,2,3\) 矩阵，一次批调用里每张图用不同参数，torchvision 的函数式算子一次只能给一个参数
- 最小解求解器和 RANSAC 全在 GPU 上跑：find_fundamental 用 7 点法一次解 \(B,7,2\) 样本、返回 \(B,3,3,3\) 全部实数解，RANSAC 在设备上采样打分，compile=True 时整段估计编成一张计算图
- 可微分几何闭环：depth_to_3d_v2 / unproject_points / project_points、warp_frame_depth、Brown–Conrady 和 Kannala–Brandt 畸变相机模型、So3/Se3 李群，梯度能对深度、位姿、相机内参回传
- 带标注的联合增强：AugmentationSequential 对图像、mask、box、关键点施加同一个采样变换并且能逆变换回去；CUDA 上采样参数直接送 GPU 不阻塞主机，还有同步守卫测试防止公开增强偷偷同步

**适用场景**: 做 SLAM、三维重建、机器人视觉、自动驾驶感知的算法工程师；需要在训练损失里嵌入几何计算（比如可微的光度误差、重投影误差、单应矩阵估计），或者想用 GPU 批量跑 SIFT/LoFTR/LightGlue 特征匹配与 RANSAC 的人。

**竞品对比**: 跟 torchvision 比，重叠只在 resize/crop/flip/颜色抖动/模糊，Kornia 多出相机模型、对极几何、最小解求解器、RANSAC、形态学、Lab/Bayer 色彩、可微损失等 1200+ 算子；跟 OpenCV/scikit-image 比，那些是 CPU 单图逐张处理、不可导，Kornia 在 RTX 4090、batch 32 下快 10~70 倍，但单张 uint8 CPU 场景 OpenCV 仍然赢。

**成熟度**: 生产可用，已到 0.9.x、有 1000+ ONNX 导出验证和公开基准页，社区与文档成熟，但仍在 1.0 之前，API 偶有调整。

**趋势信号**: 0.9.1 刚发布，主打"设备端校验去掉主机同步"和完整基准/导出支持页，加上 Spatial AI、三维重建和机器人视觉这波需求正把几何计算往 GPU 和可微方向推。

### [hyprwm/Hyprland](https://github.com/hyprwm/Hyprland)

 `C++` ⭐ +38 今日新增 · 39,494 总星数

> Hyprland 是一个自己从零写的 Wayland 平铺窗口管理器（compositor，负责画窗口、管输入的那层），主打好看的动画和极致可定制，现在已甩开 wlroots 自研后端，所以能做出别家做不了的视觉效果。

**亮点**

- 主动砍掉 wlroots 这层现成的地基，换成自研 Aquamarine，代价是自己维护后端，换来的是渲染管线和 Wayland 新协议（IME、input panel 等）能第一时间跟进，不用等上游合并
- 定位不只是窗口管理器，而是可编程平台：socket IPC + C++ 插件 + Lua 布局，让用户用脚本改窗口行为，而不只是改配置项

**核心功能**

- 不再依赖 wlroots，自己写了后端库 Aquamarine 直接对接 DRM/KMS 显示、libinput 输入和 Wayland 协议，渲染走 OpenGL ES，所以渐变边框、多层模糊、外发光、阴影这些效果可以自己控制，不受 wlroots 架构限制
- 动画用自定义的贝塞尔曲线和 spring（弹簧）曲线驱动，配置文件里能给每类动画单独设曲线参数；另有 tearing（允许屏幕撕裂）开关，开了能降低游戏画面延迟
- 基于 Unix socket 的 IPC，外部脚本可以查询/控制窗口和 workspace；插件编译成 .so 由内置插件管理器加载，布局可以用 Lua 或插件自己写（内置 dwindle/scrolling/master/monocle 四种）
- 配置文件改完保存即生效，compositor 热重载不重启——重启会杀掉所有窗口，这点在平铺 WM 上是刚需

**适用场景**: Linux 桌面折腾党（ricing 玩家）拿它当日常窗口管理器，配 waybar 状态栏、wofi 启动器、hyprpaper 壁纸一起用；需要多显示器、每个 workspace 用不同布局、或者打游戏想要低延迟的人也会选它。

**竞品对比**: 和 Sway 比，Sway 走 wlroots + 极简路线，稳定但基本没有动画和模糊；和 KDE 的 KWin、GNOME 的 Mutter 比，那俩是完整桌面环境，Hyprland 只管窗口管理，但视觉效果和配置自由度更高；和 Niri（Rust 写的滚动式平铺）比，Niri 强调工作流模型，Hyprland 强调观感和插件生态。

**成熟度**: 生产可用但仍是 0.x 版本（0.5x），配置语法和插件 ABI 时不时会变，升级前要读更新日志；开发非常活跃，Wiki 文档质量不错，插件和主题生态已经成型。

**趋势信号**: 刚完成从 wlroots 到自研 Aquamarine 后端的切换，又加了 Lua 配置/布局和内置插件管理器，加上 ricing 社区的截图和视频一直在扩散，热度持续被推高。

## 趋势观察

这批项目有个共同点：没人再卷模型本身，全在卷模型外面那层。第一件事是给 Agent 装记忆和调度。压缩工具调用轨迹、49 个 Agent 分工的仿游戏工作室、手机远程接管本机 Claude Code，都是在解决同一个问题——Agent 能干活了，但记性差、管不过来。第二件事是本地优先。两个离线语音听写、单卡跑 290B MoE 的推理引擎、自托管的 AI 安全运营中心、每个 bot 一台容器的 CopilotKit，思路一致：数据不出门，订阅不重买，机器钱要省。那个用 Zig 写的无头浏览器，省 16 倍内存，就是给 AI 抓网页算账。第三件事是垂直资产开始变成可运行的数据。K 线基础模型把行情量化成 token，紫微斗数把口传内容做成 67 万张命盘，都是把行业知识变成模型能吃的格式。还有一条暗线是安全：32 份提示词专门研究指令层级怎么被绕过，说明大家心里清楚，Agent 越能动手，越要有人批准和可回放的审计。新闻热点是各家闭源个人 Agent 扎堆发布，开发者生态的反应很直接——本地优先的开源替代、免费 API 清单、93 个能跑起来的小项目。大家不想听概念，想今晚就把东西跑起来。总的说，2026 年的竞争点不在谁的模型聪明，在谁的 Agent 记得住、管得动、跑得起、查得清。
