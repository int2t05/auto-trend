**竞品对比**: 相比 Mem0、Letta 这类偏个人记忆方案，它主打团队级共享和管理，强调资源审核、版本、权限池和跨 Agent 装备，更像企业级记忆中台。

**成熟度**: 仍处于 Beta（v3 刚出迁移工具），API 可能变动，但文档齐全、安装脚本一键启动，适合尝鲜和小规模试用。

**趋势信号**: AI Agent 开发正从“单会话”转向“多 Agent 协作”，记忆和上下文复用成了刚需；这个仓库今天涨了近 2000 星，可能是腾讯开源背书加满足团队记忆痛点。

### [firecrawl/pdf-inspector](https://github.com/firecrawl/pdf-inspector)

 `Rust` ⭐ +1,582 今日新增 · 11,598 总星数

> 用 Rust 写的 PDF 解析库，能快速识别 PDF 是文本还是扫描版，把文本 PDF 直接转成 Markdown，不用 OCR。现在因为 AI 数据抓取需要快速处理 PDF 而火。

**亮点**

- 文档只加载一次，检测和提取共享解析结果，避免重复 I/O
- 用矩形检测+启发式对齐两种模式识别表格，还能处理跨页连续表格

**核心功能**

- 用采样内容流的方式在 10-50ms 内判断 PDF 类型（文本/扫描/图片/混合），并给出置信度，支持按页路由 OCR
- 支持 CID 字体和 ToUnicode CMap 解码，能处理 Type0/Identity-H 字体，提取带坐标和字体信息的文本
- 纯 Rust 实现，无 ML 模型，单依赖 lopdf，可编译为 WASM 在浏览器本地运行

**适用场景**: 做文档解析、RAG 数据管道的开发者，需要把大量 PDF 快速转成干净的 Markdown 喂给大模型，比如 AI 搜索、知识库、财务/法律文档处理。

**竞品对比**: 比 PyMuPDF4LLM、MarkItDown 快几十倍，在阅读顺序和表格提取上得分更高；和 Liteparse 接近但更快。无需 OCR 就能处理文本 PDF。

**成熟度**: 早期项目（0.2.x），但有 Firecrawl 团队维护，提供多语言绑定和 CLI，已有基准测试验证，API 可能还会变。

**趋势信号**: 因为 RAG/LLM 应用需要把 PDF 转 Markdown，而现有方案要么慢要么质量差；Firecrawl 团队背书+基准测试第一，今天涨了 1582 star。

**亮点**

**核心功能**

- 支持无后端模式，单独暴露虚拟文件系统，可以直接当持久化存储用；后端懒连接，首次执行才启动

**竞品对比**: 比 E2B、Modal sandbox 这类 agent 沙箱更贴近 Cloudflare Workers 生态，区别是状态由 Durable Object 统一管理，后端可插拔，不绑定容器。

### [lyogavin/airllm](https://github.com/lyogavin/airllm)

 `Jupyter Notebook` ⭐ +833 今日新增 · 29,185 总星数

> AirLLM把大模型按层切分，逐层加载到显存计算，让70B模型在4GB显卡上运行，近期因支持2.8T的Kimi K3走红。

**亮点**

- 不靠量化或蒸馏，而是用磁盘换显存，把模型切成层顺序加载，配合预取重叠读写和计算，这是和其他低显存推理方案最大的区别。
- 对MoE模型按专家而不是整层流式加载，利用稀疏路由特性，让超大规模模型在极小显存下运行成为可能。

**核心功能**

- 按层流式加载：模型权重按层从磁盘读入GPU，算完就释放，显存占用只和单层大小相关，所以4GB能跑70B。
- 支持块级量化压缩（block-wise quantization），用bitsandbytes把权重压到4bit/8bit，加载量变小，推理提速约3倍。
- 对MoE模型按专家粒度流式加载，只加载当前token路由到的专家，所以2.8T的Kimi K3只需3.72GB显存。

**适用场景**: 没有高端GPU的个人开发者或小团队，想在本地跑Llama 70B、DeepSeek-V3等大模型做推理测试或私有化部署，用一张消费级显卡就能完成。

**竞品对比**: 相比llama.cpp的CPU offload和ExLlama的量化，AirLLM主打无需量化就能跑超大模型，但受磁盘读取限制推理速度较慢，更偏离线批处理而非实时交互。

**成熟度**: 项目活跃，已发布v3.0，但API随新模型更新可能变动，文档齐全，生产使用需自行验证稳定性。

**趋势信号**: 2026年7月支持了Kimi K3（2.8T参数）——目前最大的开源模型，在单张4GB显卡上跑通，直接引爆社区对消费级硬件跑超大模型的热情。

- /build auto 模式：审批计划后自主实现所有任务，但仍保持每任务 TDD 和独立提交，遇险暂停——把人的介入从任务间移除，而不是移除验证

**核心功能**

- 8 个斜杠命令（/spec、/plan、/build 等）映射开发全生命周期，自动激活对应技能，其中 /build auto 支持一次审批后自主执行所有 TDD 任务
- 技能以纯 Markdown 打包，通过 Vercel skills CLI 可安装到 70+ 种 agent（Claude Code、Cursor、Codex 等），也支持原生插件集成
- 每个技能含结构化步骤、验证门和反合理化表，强制 agent 遵循如测试先行的工程纪律

**适用场景**: 使用 AI 编码 agent 的开发者或工程团队，在 Claude Code、Cursor、Copilot 等工具中需要标准化开发流程、质量门禁时，安装此包让 agent 按规范执行。

**竞品对比**: 同领域有各种 prompt 集合或规则文件，但此项目是系统化的生命周期技能包，且跨 agent 兼容。最大差异点是结构化验证门和自动技能激活。

**成熟度**: 生产可用，已支持多种主流 agent 并有详细文档，社区广泛采用（8 万+ stars）。

**趋势信号**: AI 编码 agent 爆发，开发者急需可复用的工程规范，加上 Vercel skills CLI 推动技能标准化，所以热度飙升。

### [vercel/next.js](https://github.com/vercel/next.js)

 `JavaScript` ⭐ +68 今日新增 · 141,576 总星数

> 基于 React 的全栈 Web 框架，提供服务端渲染、静态生成、API 路由和文件系统路由，适合构建 SEO 友好的现代 Web 应用。

**亮点**

- 采用 React Server Components 将组件渲染放在服务端，客户端只传输交互部分，显著减少包体积
- Turbopack（基于 Rust）作为打包器，比 webpack 更快

**核心功能**

- 内置 App Router 和 React Server Components，页面组件可直接在服务端读取数据库，减少客户端 JS
- 自动代码分割和基于文件系统的路由，pages/api 直接生成后端接口
- 支持静态生成（SSG）、服务端渲染（SSR）和增量静态再验证（ISR），按需选择渲染策略

**适用场景**: React 开发者构建需要 SEO 的营销页、内容站点或全栈小应用，适合需要服务端渲染/静态生成的场景。

**竞品对比**: 相比 Gatsby 更强调服务端能力，相比 Astro 支持更多服务端交互，相比 Nuxt（Vue）是 React 生态首选全栈框架。

**成熟度**: 生产可用，版本已到 15，广泛用于企业级项目，社区和文档成熟。

**趋势信号**: 近期发布 Next.js 15 并稳定支持 React 19，加上 App Router 成为默认推荐，推动现有用户升级和项目迁移。
