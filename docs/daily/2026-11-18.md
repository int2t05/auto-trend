# GitHub Trending 日报 · 2026-11-18

## 概览

今日共收录 **15** 个 GitHub Trending 项目。
主要语言分布：TypeScript(5)、Python(4)、Go(3)、JavaScript(2)、Shell(1)。

今天这批项目，几乎都在干同一件事：给 AI Agent 修路、装护栏、定规矩。先说技能包。漏洞红队、跨平台搜社区讨论、Stitch 设计稿转代码，都被打包成一个个可加载的 Skills。这说明技能正在变成新的分发单位，像当年的 npm 包，谁把好用的技能攒成包，谁就占住入口。再看大厂动作。阿里把内部用了两年的代码评审 CLI 开源，腾讯把 10 种编码 Agent 编排成带 Docker 沙箱和人工审批的 SOP。这是个明确信号：Agent 交付开始要可重复、可审计，不再靠人肉盯。第三个信号是协作界面被补上了。Plannotator 弹出评审面板让你划线批注，腾讯流程里有人工审批门，事件流规范给人工确认留了位置。大家逐渐接受一个事实：Agent 干活，人得能在关键节点插手。还有一层是跨工具复用。一个仓库适配 18 种 Agent，外挂层统一管技能和记忆，Cursor 开放插件市场，这些都在解决同一个痛点——别为每个工具重写一遍接线。Google 的多智能体写论文、3 块钱手搓 64M 小模型，则把门槛继续往下压。总的看，开发者生态的关注点已经从「Agent 能不能跑」，转向「怎么让它跑得稳、看得见、能复用」。技能包、插件规范、工作流编排、人机评审面板，就是这条路上的四块砖。真正的竞争，正在从模型本身，转移到模型外面那层流程和标准上。

### [obra/superpowers](https://github.com/obra/superpowers)

 `Shell` ⭐ +1,917 今日新增 · 319,556 总星数

> 给编程 Agent 装一套开发流程：先反问需求、出规格、写实现计划，再派子 Agent 按 TDD 逐项做完。一个仓库适配 18 种 Agent。

**亮点**

- 不造新 Agent，只改行为：方法论全部写成提示词注入宿主 CLI，所以能寄生在十几家的插件市场里，不跟任何一家绑定
- 计划写得刻意'降级'——要求细到没上下文、不爱写测试的初级工程师也能照做；再配子 Agent + 审阅循环，让主 Agent 能连续自主工作几小时

**核心功能**

- 把'头脑风暴 → 规格 → 实现计划 → 执行'拆成一组可组合的 skill 文件。主 Agent 只做调度和审阅，具体编码交给子 Agent，一次只推进一个任务，做完再检查再往下走
- 靠宿主 Agent 的插件系统分发，同一份 skill 装进 Claude Code、Codex、Cursor、Gemini CLI、Copilot CLI、Devin、Qwen Code 等 18 个 harness，安装脚本是纯 Shell，没有自己的运行时
- 对话一开始就注入一个引导 skill（using-superpowers），逼 Agent 先别写代码、先问清你到底要做什么；上下文压缩后会重新注入，Pi 和 Claude Code 有 hook 能做，Hermes 没有 hook 就会丢

**适用场景**: 用 Cursor / Claude Code / Codex 写业务代码的工程师和团队。适合需求还模糊、要先对齐再动手的中大型改动，以及想让 Agent 自己跑几个小时不跑偏的场景。

**竞品对比**: 对标 GitHub Spec Kit、BMAD-METHOD 这类规格驱动工作流。差别是 Spec Kit 绑 Copilot/Claude 单一栈，BMAD 靠角色扮演；Superpowers 直接装进各家官方插件市场，并且多了子 Agent 执行和审阅这一层。

**成熟度**: 已进 Anthropic 官方市场和 OpenAI 插件市场，有商业支持渠道，但本质是 Shell 加提示词，效果强依赖宿主模型，接口还在频繁变。

**趋势信号**: Anthropic 推 Agent Skills、OpenAI/Cursor/Gemini/xAI 同期都上线了插件市场，Superpowers 一次性进了其中好几家官方商店，成了'跨 harness 通用 skill 包'的现成样板。

**核心功能**

- 跨 harness 适配层：把技能、规则、记忆抽成代理工具之外的一层，通过 Claude Code 插件（ecc@ecc）和 npm 包 ecc-universal 分发到 Claude Code、Codex、Cursor、Opencode 等 7 个工具，换工具不用重写配置
- 技能（skills）与“直觉”（instincts）两层：技能是可直接执行的常用操作包，直觉是判断规则（遇到某类情况该怎么做），代理不用每次从零推理，直接命中对应条目
- 自带 ecc-agentshield 安全包和“研究优先”流程：让代理先查证代码库再动手改，配合安全检查降低乱改文件、乱跑命令的概率

**适用场景**: 已经在用 Claude Code 或 Cursor 写代码的个人开发者和小团队，尤其是同时用两三个代理工具、希望统一工作流和规则的人；也适合想把代理行为约束成团队规范的技术负责人。

**竞品对比**: 和 SuperClaude、BMAD-METHOD、claude-flow 这类 Claude Code 增强框架同赛道，最大差别是不绑定单一工具、要覆盖 7 个 harness，并且直接做成了可一键安装的插件和付费托管服务。

**成熟度**: 已投入实际使用（有多语言文档、Discord、赞助商和 Pro 订阅），但单维护者项目，且 305k star 与项目体量、提交活跃度对不上，选型前建议自己核对 changelog 和 issue 响应。

**趋势信号**: Claude Code、Codex、Cursor 今年集体爆发，各家的 skill 和规则格式互不兼容，“一套配置跨工具复用”正好对准这个痛点，所以冲上 trending。

### [cursor/plugins](https://github.com/cursor/plugins)

 `TypeScript` ⭐ +201 今日新增 · 16,995 总星数

> Cursor 官方插件仓库，给出插件规范（每个插件目录下一个 .cursor-plugin/plugin.json 清单）并配套一批官方插件。作用是让编辑器里的编码 Agent 能直接调用 SaaS 工具和自己的团队工作流。现在火是因为 Cursor 正式开放了插件市场。

**亮点**

- 把“Agent 怎么用工具”从口头提示变成可复用资产：插件里存的是技能加 CLI 封装，而不是插件里再塞一堆 prompt。像 cli-for-agent 直接把幂等、dry-run、结构化报错这些设计约束写成规范
- 第三方集成统一收在 third_party/ 下，每个 SaaS 一个插件；Salesforce 还专门另开一个 Beta 的 Headless 360 版本，说明它在试探“老式有界面 API”和“纯 API”两套接入方式

**核心功能**

- 用目录级 .cursor-plugin/plugin.json 做插件清单：一个插件就是一个独立目录，内含清单、技能和脚本，安装时按目录隔离，不会互相污染
- 插件本质是给 Agent 安装“技能包”加上封装好的 CLI 调用：比如 playwright 插件让 Agent 在真实浏览器里点击截图，gmail/google-drive/zoom 等是把第三方 API 封装成 Agent 能可靠调用的命令
- 专门有一个 cli-for-agent 插件，总结“怎么设计让 Agent 跑得稳的 CLI”：必备 --dry-run、幂等、带示例的 --help、结构化错误输出和可管道化，等于把 Agent 调工具的踩坑经验写成了规范
- 几个编排类插件走了多子代理路线：thermos 用并行子代理做安全/正确性审计，orchestrate 把大任务拆成 planner/worker/verifier 分组并行下发到云端 Agent，再按结构化协议交接

**适用场景**: 用 Cursor 写代码、又想让 Agent 直接查询 Salesforce 记录、拉取 Gong 通话摘要、查看 GA4 报表或提交 PR 的开发者和业务团队。团队还可以用 cursor-team-kit、pstack 这类插件把内部 CI、代码评审和交付流程固化成 Agent 工作流。

**竞品对比**: 和 Anthropic 的 Claude Code 插件与 Skills、以及 MCP（把外部工具统一暴露给模型的协议）正面竞争。最大差异是 Cursor 把插件、技能、子代理编排和自家 IDE 市场绑在一起，用户点一下就能装；MCP 是通用协议，需要自己托管服务器。

**成熟度**: 早期阶段：插件规范刚公开，不少第三方插件标着 Beta，规范本身可能还会改。

**趋势信号**: Cursor 上线插件市场、正式开放插件规范，这是它把“技能生态”做成平台护城河的动作，紧跟着 Claude Code Skills 的节奏。

### [jingyaogong/minimind](https://github.com/jingyaogong/minimind)

 `Python` ⭐ +192 今日新增 · 66,272 总星数

> 用 PyTorch 从零手写 64M 小模型的整条训练链，在单卡上花 2 小时、约 3 元就能跑完预训练到 RLHF，适合亲手弄懂 LLM 原理。

**亮点**

- 把规模压到 64M（GPT-3 的 1/2700）并用精简清洗过的数据，让"完整训一遍"变成能反复做实验的事，而不是只能读论文
- 刻意不用 transformers/trl 的封装，但权重命名和 chat_template 又对齐 transformers，导出的模型能直接喂给 llama.cpp / vllm / ollama，学习和实用两头都不丢

**核心功能**

- 预训练、SFT、LoRA、DPO、PPO、GRPO、CISPO、蒸馏全部用 PyTorch 原生手写，不调 trl/peft 的高层接口；连 LoRA 的低秩矩阵更新、DPO loss 都是自己实现的
- minimind-3 结构对齐 Qwen3 和 Qwen3-MoE（Dense 64M，MoE 198M 总参，激活 64M，去掉了 shared expert），Tokenizer 换成 BPE + ByteLevel，并预留 &lt;tool_call&gt;/&lt;think&gt; 等特殊标记
- RLAIF 和 Agentic RL 把 rollout engine 解耦，生成后端可以更换；多轮工具调用场景直接跑 GRPO/CISPO，长文本用 YaRN 对 RoPE 做外推

**适用场景**: 想搞懂大模型内部原理的学生和工程师，用自己的 3090 或几块钱租的算力从头跑一遍预训练→SFT→RLHF；也适合高校课程和培训班当作教学 demo，因为每一步都能看到代码。

**竞品对比**: 对比 Karpathy 的 nanoGPT（只做预训练、英文数据、没有 SFT 和 RLHF）和 Datawhale happy-llm 这类中文教程，MiniMind 把 DPO/GRPO/Agentic RL、工具调用也手写了一遍，还配了中文数据和 OpenAI 兼容服务端。

**成熟度**: 已迭代到 v3、66k star、更新日志和中文文档很全，但定位是教学和实验，64M 模型的对话质量不能当生产模型用。

**趋势信号**: 2026-04 发布 minimind-3，结构对齐 Qwen3/Qwen3-MoE 并新增 Agentic RL（GRPO/CISPO）训练脚本，正好赶上大家想自己复现 RL 训推理模型的热度。

### [dream-num/univer](https://github.com/dream-num/univer)

 `TypeScript` ⭐ +1,774 今日新增 · 29,476 总星数

> Univer 是一个开源 Office SDK，能把表格、文档的编辑、公式计算和协作嵌进自己的产品，也能不开界面直接跑在服务端处理文件。最近主打「给 AI Agent 用的办公内核」重新包装，所以冲上热榜。

**亮点**

- 把「Office 内核」和「Office 界面」拆开，headless 模式复用同一套计算和内容模型，这是它能接 Agent 的前提
- 开源核心（Apache-2.0，含表格/文档编辑、公式、渲染）+ 商业插件、Server SDK、AI SDK 分层授权，开源部分负责拉生态，赚钱靠协作和文件转换

**核心功能**

- 插件化内核加依赖管理：公式、渲染、UI、协作各是独立包，装哪个开哪个，不用为一格表格拖进整个编辑器
- 所有编辑都走统一命令系统（command），改单元格、改公式、撤销重做是同一条链路，跨功能的组合编辑和 undo/redo 不会打架
- 同一套内容模型和公式引擎两用：浏览器里是可视化编辑器，去掉 UI 就是 headless，服务端可以直接算表、导入导出文件
- 对外用 Facade API 加事件暴露能力，外部应用或 Agent 通过它读写文档，不用碰内部数据结构

**适用场景**: SaaS 产品想在自家系统里塞一个在线表格或文档编辑器（比如项目管理工具加甘特表、CRM 加报价单），不想从头写渲染和公式引擎。 AI 团队想让 Agent 读写 Excel/文档：Agent 负责调模型和编排工具，Univer 负责真正的表格计算和文件处理。

**竞品对比**: 和 Luckysheet（Univer 团队的前身项目，已基本停更）、SheetJS（只解析文件不负责编辑）比，Univer 是完整的可嵌入编辑内核；和 AG Grid、OnlyOffice 比，差异在于能 headless 跑、且明确面向 Agent 开放 API。

**成熟度**: 核心已相当成熟：约 3 万 star、多语言文档、CI 和覆盖率齐全、有实际企业集成；但开源只覆盖 Web SDK 核心，实时协作和 Office 文件导入导出属于商业授权，选型时要算清授权成本。

**趋势信号**: README 从「开源表格」改写成「Build your own AI office」，新增 AI SDK、CLI 和 agent 集成，正好赶上各家把 Agent 接进文档和表格的这波需求。

### [ag-ui-protocol/ag-ui](https://github.com/ag-ui-protocol/ag-ui)

 `TypeScript` ⭐ +1,445 今日新增 · 20,165 总星数

> 用一套带类型的事件流，把任意 AI Agent 接到前端应用：流式输出、工具调用、共享状态、人工确认全走同一份 1.0 规范，不用再为每个框架写一套前端接线。

**亮点**

- 把 agent 通信明确拆成三段互不冲突的职责：MCP 管工具和上下文，A2A 管 agent 之间互相调用，AG-UI 只管 agent 到人这一段。它不争夺前两者的职责，只补上最后一段
- 1.0 规范一旦冻结，就保证双向兼容：0.x 的 agent 能和 1.0 的客户端通信，反之亦然，因此后端框架和前端 SDK 可以各自独立升级

**核心功能**

- 所有交互都抽象成带类型的 SSE 事件：RunStarted、TextMessageContent（逐字增量）、ToolCall、StateDelta、RunFinished。Agent 端只要提供一个 HTTP 接口，接收 RunAgentInput 并返回事件流，用 EventEncoder 按 Accept 头决定编码格式
- 协议本身用 JSON Schema 定义，TypeScript、Python、.NET 三套 SDK 都从同一份 schema 生成，避免一份协议在三种语言里各实现一遍、还互相不一致
- 支持反向调用和增量同步：agent 可以调用前端注册的浏览器端函数（前端工具），共享状态通过 StateDelta 增量推送，不必每次全量重发
- 事件流发送到哪儿由客户端负责：同一份接口能交给 Web、移动端、终端、Slack 渲染，更换后端框架时前端不用改动

**适用场景**: 已经用 LangChain、CrewAI、Google ADK、Microsoft Agent Framework 做完 agent 后端，但要在前端实现流式渲染、工具回调、人工确认拦截和子 agent 状态展示的团队。典型组合是 CopilotKit + Next.js 的聊天界面，或企业内部 Slack、Teams 机器人。

**竞品对比**: 竞品主要是 Vercel AI SDK 的 data stream 协议和 OpenAI Responses 的流式接口。差异在于 AG-UI 与框架、模型厂商无关，并且明确是双向事件流：agent 能回调前端工具、请求人工确认，不只单向返回 token；MCP 只解决工具，不管用户界面这一段。

**成熟度**: 生产可用：1.0 规范已冻结并配 JSON Schema，SDK 自动生成，MIT 许可，Google、Microsoft、Amazon、Oracle 已接入；但 1.0 刚发布，部分框架适配还在补。

**趋势信号**: AG-UI 1.0 稳定规范刚发布（含 JSON Schema 和三语言生成 SDK，且双向向后兼容），又赶上 Microsoft Agent Framework、Google ADK 等框架密集接入，当各框架都在寻找 agent 前端落地标准时，它被推到了台前。

### [google-research/paper-orchestra](https://github.com/google-research/paper-orchestra)

 `Python` ⭐ +1,072 今日新增 · 3,414 总星数

> Google Cloud AI Research 的多智能体流水线，把想法和实验日志变成带文献综述、图表、会议 LaTeX 模板的投稿级论文初稿。

**亮点**

- 没有用一个巨型 prompt 硬写全文，而是拆成有明确上下游的 Agent 流水线，大纲、综述、图都是可单独替换和人工干预的中间产物

**竞品对比**: 对比 Sakana 的 AI Scientist（连实验一起做）和 GPT-Researcher（出调研报告），它只做“写作”这一段，但交付物是符合会议模板的 LaTeX 加代码生成的真图，更贴真实投稿流程；和 STORM 的维基式长文也不是一个目标。

**成熟度**: 研究原型：训练/评测数据集还没放出来，无版本号，README 明确写着非 Google 官方支持产品，接口和生成质量都还会变。

**趋势信号**: 正值 arXiv 和会议对 AI 代写论文的争议升温，又挂着 Google Cloud AI Research 的名头，一天涨一千多星更多是话题驱动而非工程成熟度。

- runes 是一次取舍明确的转向——从"编译期猜哪些变量是响应式的"改成"显式声明 signal"，牺牲了一点写法简洁度，换来跨文件复用、可测试和更可预测的更新粒度

**核心功能**

- 编译期把声明式组件翻译成直接操作 DOM 的 JS，运行时不带虚拟 DOM diff 那一层，打包产物里框架本身的开销被压到很小
- Svelte 5 的 runes（$state/$derived/$effect）用细粒度 signals 做响应式：改一个值只重跑依赖它的那段代码，而且响应式逻辑能写进普通 .svelte.js 文件复用，不再绑死在组件的顶层 let 上
- 编译器用 JavaScript 写、靠 JSDoc 注释做类型检查而不是 TypeScript，省掉一层构建依赖；组件内的 &lt;style&gt; 编译时加哈希类名并剔除没用到的选择器，样式能跟着组件一起被 tree-shake

**适用场景**: 做营销页、内容站、后台面板的前端团队，尤其是对首屏 JS 体积敏感、又不想写太多样板代码的场景；配 SvelteKit 做 SSR/SSG 站点，或用它写嵌入式 widget 塞进别人的页面。

**竞品对比**: 对比 React 是虚拟 DOM diff + hooks 依赖数组，对比 Vue 是响应式但带 runtime，Svelte 走的是编译期消除框架的路；和同样用细粒度 signals 的 Solid 相比，Svelte 更强调模板语法和"零 runtime"，Solid 更贴近 JSX 写法。

**成熟度**: 生产可用：5.x 已稳定发布，文档完善，社区和贡献者规模大，Apple、Spotify 等有实际线上使用；但 5 的周边生态（组件库、教程）还在从 4 迁移中。

**趋势信号**: Svelte 5 的 runes 迁移正在铺开，同期 Angular signals、Vue Vapor、Solid 都在往细粒度响应式靠，signals 成了前端共识，Svelte 作为最早一批把这条路线做进主流框架的项目被反复提起。

- react-components / react-native 两个 skill 带自动校验和设计 token 一致性检查，支持对同一个 Stitch 项目 ID 反复 sync，改了设计稿就增量更新组件而不是全量重生成
- 安装走 Codex 插件市场（支持 --sparse 只拉需要的路径）或 npx plugins add，Claude Code 装到 project 作用域、Cursor 装到 workspace 作用域，OpenCode 因为不支持这套布局得手动拷目录并改 kebab-case 命名

**适用场景**: 前端和全栈工程师在 Cursor / Claude Code 里写业务代码时，让 Agent 直接从 Stitch 的设计稿生成 React 组件或 React Native 页面，省掉手抄 Figma 标注 设计师和前端一起维护设计系统：用 extract-design-md 把现有代码里的 token 抽成 DESIGN.md 传回 Stitch，再让 Agent 按新主题批量刷所有屏幕 需要做产品演示或融资材料的团队，用 remotion skill 从 Stitch 项目自动生成带镜头推移和缩放的 walkthrough 视频

**竞品对比**: 对标的是 Figma MCP + 各类 Figma-to-code 插件、以及 v0 / Lovable 这类「描述生成 UI」工具。最大差异是它不绑定自家客户端——同一套 Skill 能跑在 Claude Code、Cursor、Codex、Gemini CLI 上，而 Figma 系方案基本围绕 Figma 自身和少数 IDE 插件；另外 Stitch 本身是生成式设计工具，起点就是可编辑的设计而非静态稿。

**成熟度**: 早期项目，靠 npm 的 npx plugins / npx skills 分发，OpenCode 还得手动改目录名，skill 之间有依赖关系容易装漏，API 和目录结构都可能变。

**趋势信号**: 直接受益于两件事叠加：Anthropic 把 Agent Skills 推成开放标准后各家 Agent 开始互认技能包，同时 Google 上线 Antigravity 和 Stitch MCP 公测，官方需要一个「谷歌设计工具 + 别家编码 Agent」的桥，这个仓库正好卡在那个位置。

## 趋势观察

今天这批项目，几乎都在干同一件事：给 AI Agent 修路、装护栏、定规矩。先说技能包。漏洞红队、跨平台搜社区讨论、Stitch 设计稿转代码，都被打包成一个个可加载的 Skills。这说明技能正在变成新的分发单位，像当年的 npm 包，谁把好用的技能攒成包，谁就占住入口。再看大厂动作。阿里把内部用了两年的代码评审 CLI 开源，腾讯把 10 种编码 Agent 编排成带 Docker 沙箱和人工审批的 SOP。这是个明确信号：Agent 交付开始要可重复、可审计，不再靠人肉盯。第三个信号是协作界面被补上了。Plannotator 弹出评审面板让你划线批注，腾讯流程里有人工审批门，事件流规范给人工确认留了位置。大家逐渐接受一个事实：Agent 干活，人得能在关键节点插手。还有一层是跨工具复用。一个仓库适配 18 种 Agent，外挂层统一管技能和记忆，Cursor 开放插件市场，这些都在解决同一个痛点——别为每个工具重写一遍接线。Google 的多智能体写论文、3 块钱手搓 64M 小模型，则把门槛继续往下压。总的看，开发者生态的关注点已经从「Agent 能不能跑」，转向「怎么让它跑得稳、看得见、能复用」。技能包、插件规范、工作流编排、人机评审面板，就是这条路上的四块砖。真正的竞争，正在从模型本身，转移到模型外面那层流程和标准上。
