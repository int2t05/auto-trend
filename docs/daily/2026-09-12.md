### [bilawalsidhu/gods-eye-view](https://github.com/bilawalsidhu/gods-eye-view)

 `JavaScript` ⭐ +2,265 今日新增 · 30,457 总星数

> 浏览器里跑的 3D「间谍卫星」地球仪，把航班、船舶、卫星、地震、公共摄像头等公开数据实时叠在一张照片级地球上，本地运行、代码全开放。

**亮点**

- 分享链接被当成「实时交接」而不是书签：URL 里序列化了相机位姿、图层、滤镜，甚至正在跟踪的那个目标 ID，别人打开看到的是同一个还在动的目标。
- 跟踪一个火点或船只后可以一键切到最近的实时摄像头，把「地图上的点」直接接到「现场画面」。
- 密钥处理相对克制：写进 .env 或 pinokio/ENVIRONMENT 之前先改成仅本人可读，来自 shell 或 macOS Keychain 的值在面板里显示为外部配置且只读。

**核心功能**

- 数据源按图层拆成独立模块：ADS-B 航班应答机、AIS 船舶信标、TLE 卫星轨道根数（算卫星位置的标准参数）、USGS 地震台网、公共摄像头，每一层可以单独换掉或自己加。
- 3D 底座用 Cesium 渲染，卫星影像默认走 Esri，地形无 key 也能加载，Esri 挂了自动回退 OSM；只有填 Cesium ion token 才升级成照片级地形，填 Google Maps key 才开地址搜索。也就是说开箱可用，key 只是画质升级。
- 视觉层用 GLSL 着色器做传感器滤镜（CRT、夜视 NVG、FLIR 热成像、黑白 Noir），另加屏幕空间检测框 + ID 标签和军事风 HUD；相机跟飞时持续把地形压在机腹下，而不是固定视角俯拍。

**适用场景**: OSINT（公开来源情报）爱好者、记者、做地缘/应急报道的编辑，以及做视频素材的创作者。以前要开 Flightradar24、MarineTraffic、N2YO 好几个网站切来切去，现在在一个地球上看某架飞机、某艘船，还能一键跳到离它最近的公共摄像头。

**竞品对比**: 单看某一层，Flightradar24、ADS-B Exchange、MarineTraffic、N2YO 都比它专业且数据更全；它的差异是把空、海、天、地震、摄像头塞进同一张 3D 地球，并且开源、本地跑、图层可自己写。对比 Palantir 那类商用态势感知平台，它相当于免费可改的玩具版。

**成熟度**: 工程化程度不低（有 CI、性能文档、启动前 doctor 检查、Pinokio 一键安装、锁定的依赖版本），但看起来仍是个人主导的活跃项目，长期维护和 API 稳定性没法保证。

**趋势信号**: 先靠 YouTube 系列视频（500 万+播放）在社交媒体爆火，再开源代码，视频观众转成 star，单日涨 2265；叠加当下 OSINT 工具热度上升。

### [p1neappleXpress/OpenFlux](https://github.com/p1neappleXpress/OpenFlux)

 `Go` ⭐ +355 今日新增 · 1,432 总星数

> Go 写的 TCP 隧道：客户端跑 SOCKS5，把流量塞进 Yandex Docs 文档消息或 MAX 聊天数据通道，再由境外出口节点转发出去。俄语区封锁收紧让它冲上热榜。

**亮点**

- 不自己搭中继基础设施，直接寄生在 Yandex Docs、MAX 这类合法云服务的现成通道上，流量在外人看来就是正常访问这些服务。
- RST 抑制按源 IP 收窄而不是全机 DROP。全机丢弃会把这台机器所有关闭端口变成"静默过滤"，扫描器看不出 closed，也影响别的服务——用户态网络栈落地时容易踩的坑，作者专门写了。

**核心功能**

- 传输层做成可插拔接口（transport/transport.go），隧道核心不关心底下用什么。现有两个后端：yandex 把 TCP 包塞进 Yandex Docs 的实时光标消息，oneme 走 MAX 聊天软件的 WebRTC DataChannel。加新传输只要实现接口再在 main.go 的 switch 里注册。
- 出口节点用 gVisor 用户态网络栈接管 TCP 连接。问题是内核里没有对应 socket，回包会被内核当成无效连接直接回 RST，隧道当场断掉。所以要对出口 IP 做 iptables RST 丢弃，README 还写明 -m owner 匹配没用——那个 RST 是内核发的，没有属主 socket。
- 客户端是 SOCKS5 服务 + 一层压缩包装，raw socket 按 Linux/macOS/Windows 各写一份，iOS 用 cgo 导出静态库 liboflux.a 给 SwiftUI 客户端链接，Android/iOS 都有现成客户端仓库。

**适用场景**: 主要是俄语区、所在网络访问受限的普通用户，装个 App 或命令行起个 SOCKS5 就能上网。另一端是手里有 Linux VPS 的技术用户，自己搭出口节点。

**竞品对比**: 跟 Xray/V2Ray、Shadowsocks、WireGuard 比，主流方案要么自定义协议再套 TLS 伪装，要么靠 CDN 和域前置，前提是你有自己的域名和服务器。OpenFlux 不用自建服务，代价是速度和稳定性完全受制于第三方 API 的限流。思路更接近 Telegram MTProto 代理和 StegoTorus 这类把流量藏进合法协议的方案。

**成熟度**: 早期项目，没有正式版本号，README 自己把 MAX 传输标成 experimental，且大量篇幅是免责声明，接口和传输实现随时可能改。

**趋势信号**: 大概率跟俄语区近期的网络封锁与协议限速有关，加上 iOS TestFlight 和 Android APK 都能直接装，降低了使用门槛，一天涨 355 星。

**适用场景**: 主要用户是俄罗斯等网络审查地区的普通 Windows 玩家，想在封堵环境下正常用 Discord 语音和 YouTube，不懂命令行，下载解压后双击 bat 就能跑。

**竞品对比**: 和官方的 bol-van/zapret-win-bundle 比，它是第三方整理的易用封装，多了服务安装、策略集合、自动更新和诊断脚本；相比商业 VPN 代理，它不改路由只做数据包伪造，延迟更低但不保证长期有效。

**成熟度**: 社区维护的脚本工具，星数很高但没正式版本号，策略会随封堵升级失效，需要用户自己换策略，属于能用但需折腾。

**趋势信号**: 俄罗斯持续收紧对 Discord 和 YouTube 的 DPI 封锁，每次封堵升级导致旧策略失效，就会冒出新一轮下载和 star。

### [max-sixty/worktrunk](https://github.com/max-sixty/worktrunk)

 `Rust` ⭐ +54 今日新增 · 7,328 总星数

> 用 Rust 写的 Git worktree 命令行工具，把 worktree 当分支一样切换和管理，专门解决并行跑多个 AI 编码 agent 时目录互相打架的问题。

**亮点**

- 把 reflink 写时复制用在构建缓存共享上：多 worktree 各自有独立的 target/ 和 node_modules 目录视图，底层磁盘块却是同一份，这是它比纯 shell 脚本封装实用的关键取舍。
- 命令设计贴合 agent 工作流：`wt switch -c -x claude feat` 一条命令建 worktree 并直接拉起 agent 进程，而不是让人先切目录再手动启动，这是把 agent 当成 worktree 生命周期的第一类公民。

**核心功能**

- 用分支名寻址 worktree，路径由可配模板自动算出来。省掉原生 git 里 `git worktree add -b feat ../repo.feat` 要重复三遍分支名再 cd 的步骤，wt switch / remove / list 三个命令覆盖日常操作。
- 用写时复制（reflink）在 APFS、btrfs、XFS 上共享 node_modules、target/ 这类构建目录，10 个 worktree 不用各自重新装依赖、重新编译，靠文件系统本身复制元数据而不是真拷内容。
- 内置 hook 系统（create、pre-merge、post-merge 等时机）加从 diff 生成 commit message，把并行 agent 的收尾流程 squash/rebase/merge/清理压成一条命令；wt list --full 还能显示每个分支的 CI 状态和 AI 生成的变更摘要。

**适用场景**: ['同时开 5-10 个 Claude Code 或 Codex 会话跑长任务的开发者，需要给每个 agent 一个独立工作目录，跑完再逐个合并、清理分支。', '需要按 PR 快速切环境的人：`wt switch pr:123` 直接跳到 PR 分支，配合 hash_port 模板让每个 worktree 起独立端口的 dev server，避免端口冲突。']

**竞品对比**: 对比原生 git worktree，差异在 UX 封装 + 构建缓存共享 + agent 集成；对比 ccmanager 这类多 agent 编排工具，它管的是 worktree 生命周期（建、切、合并、清理），不是管 agent 会话本身，两者可叠加使用。

**成熟度**: 去年才发布的新项目，没有 1.0 版本号，但已有完整文档站 worktrunk.dev、CI 和 codecov 覆盖率，作者响应积极；API 和命令细节可能还会变。

**趋势信号**: 2025 年起 Claude Code、Codex 这类能长时间无人值守跑的 agent 普及，并行开多个会话成了主流用法，而 git worktree 恰好是对的工具但原生 UX 太烂，这个项目正好卡在这个缺口上被推起来。
