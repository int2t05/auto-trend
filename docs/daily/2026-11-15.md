## 概览

### [dream-num/univer](https://github.com/dream-num/univer)

 `TypeScript` ⭐ +495 今日新增 · 25,085 总星数

> Univer 是一个开源的 Office 文档引擎 SDK，用 TypeScript 编写，可以在你的产品里嵌入表格和文档编辑、公式计算，并且让 AI Agent 通过同一套 API 操作这些文档。它最近把定位改成“AI office SDK”，因此热度上升。

**亮点**

- 把“给人和给 Agent 用”统一到同一套 API：人类点击操作和代码调用走同一条命令通路，因此 Agent 的每一步修改天然支持撤销、审计和协同。
- 开源核心与商业插件切分清楚：编辑器核心、公式、渲染使用 Apache-2.0 许可证，实时协同、Office 文件导入导出、AI 扩展拆到商业版单独授权，属于典型的开放核心（open core）模式。
- 插件之间可以互相调用，但边界靠依赖注入划定，因此新功能可以挂到已有功能上，不用修改原来的代码。

**核心功能**

- 整个引擎采用插件化设计：表格、文档、公式、渲染分别是独立插件，并用依赖声明管理加载顺序，因此你可以只引入 Sheets Core 这一个预设，从而去掉不用的模块。
- 所有编辑动作都通过同一套命令系统（command）执行，因此跨插件的一次操作可以合并成一条记录，撤销和重做会像整体一样回退，而不会出现公式已经改好、单元格样式没跟着回退的情况。
- 包含自研的公式计算引擎和基于 canvas 的渲染引擎，并提供 Facade API（面向应用的封装层），让外部应用或 Agent 不需要接触内部模型，就能读写单元格、执行命令、监听事件。
- 内容模型、快照格式和计算引擎可以脱离 UI 单独运行，用来做 headless 处理：在服务端批量算公式、改文件，不启动编辑器。

**适用场景**: 适合想把表格或文档能力嵌进自家产品的团队，比如 SaaS 做报表、低代码平台做数据表格、在线教育做作业批改。也适合想让 AI Agent 读写 Excel、文档的场景：Agent 通过 Facade API 调用命令修改内容，再由应用自己管理模型和工具编排。

**竞品对比**: 和 Luckysheet（同一团队的前身项目）相比，Univer 是重写版，采用 TypeScript 和插件架构，公式与渲染更完整；和 Handsontable、AG Grid 相比，后两者只做表格控件，Univer 还包含文档和公式引擎；和 OnlyOffice、Collabora 这类完整办公套件相比，Univer 不提供成品应用，只提供可嵌入的 SDK。最大差异是原生面向 Agent 的 Facade API 和 headless 计算能力。

**成熟度**: 核心引擎已经可以被生产环境使用，有多年的迭代和 25k stars，但协同、文件导入导出这些关键能力在商业版里，开源部分单独使用时会受到限制。

**趋势信号**: README 最近改成“Build your own AI office”主打 AI SDK 和 agent 接入，正好赶上各家都在找“让 Agent 操作表格文档”的现成工具接口。

### [martin-olivier/airgorah](https://github.com/martin-olivier/airgorah)

 `Rust` ⭐ +270 今日新增 · 6,015 总星数

> 用 Rust + GTK4 写的 Linux WiFi 审计图形工具，把抓握手包、去认证攻击、跑字典破解串成一个界面，省去手敲 aircrack-ng 那堆命令。

**亮点**

- 不让整个图形程序跑 root，而是把特权操作收进一个小小的 agent 进程里，这是很多同类 GUI 工具（直接 sudo 起整个界面）没做对的地方
- 把 aircrack-ng 里需要开多个终端、记一堆参数的多步流程压进一个窗口的状态机，降低了上手成本，但本质还是那套工具的壳

**核心功能**

- 权限做了拆分：GUI 以普通用户运行，需要抓包或发包时通过 polkit 拉起一个小的特权进程 airgorah-agent，只弹一次认证，X11 和 Wayland 下都正常
- 流程是标准的 wpa 破解套路：网卡进监听模式抓包 → 发去认证帧逼客户端重连 → 抓 WPA 四次握手和 PMKID → 交给破解环节，底层依赖 aircrack-ng 那套工具
- Rust 写核心逻辑、GTK4 画界面；硬性门槛是网卡必须支持监听模式和包注入，不支持就直接用不了

**适用场景**: 渗透测试人员和安全方向的学生做自己网络的授权测试，或者打无线渗透靶场时不想再背 airodump-ng、aireplay-ng 的参数；也在 Kali/Arch 上做现场 WiFi 排查时用。

**竞品对比**: 功能上对标 aircrack-ng（命令行原版）和 Wifite（Python 写的自动化 CLI），界面体验对标已停更的 Fern WiFi Cracker；最大差异是 Rust + GTK4 的现代界面加上 polkit 权限模型。

**成熟度**: crates.io 已发版、有 CI 和 wiki 文档，但基本是单人维护、强依赖特定网卡，属于能用但别指望企业级支持。

**趋势信号**: 安全工具这两年从命令行往图形化、往 Rust 重写是明显趋势，这个项目近期版本更新后被社区转发冲上了 trending。

### [JuliusBrussee/caveman](https://github.com/JuliusBrussee/caveman)

 `Go` ⭐ +227 今日新增 · 120,174 总星数

> 把编码 Agent 的废话和日志一起压缩：回答改用穴居人腔，工具输出先瘦身，号称省 65% token。现在因 4.0 发布六件套和外部 A/B 验证上 Trending。

**亮点**

- 有意不动用户的 prompt：引用 Adobe 的结论，把用户提问也“穴居人化”反而让答案变差，所以只压 Agent 自己的输出和它读到的工具输出。
- 以 skill + 代理形式挂在 30 多个 Agent 外面，复用你已有的订阅和 API key，不换模型也不改工作流，并且每个模块都能单独开关（caveman off browse）。

**核心功能**

- 输出侧只改说话方式、不改代码：回答按 ASD-STE100 受控英语写（飞机维修手册那种简化英语，一句一个意思、不超 20 词、主动语态），代码、路径、报错逐字符照抄；README 里的 React 例子从 63 token 降到 20。
- 输入侧压缩：模型读日志、JSON、CSV、测试输出前先精简再喂进去，54 次 Claude Code 会话统计整体输入 token 少 33.2%，18 个答案全对。
- Blocks 代码模式：Agent 第一次写的测试脚本存下来复用，不用每次重新生成，跑一次测试从 397 token 降到 76；配套的 Auto 按任务挑模型和推理档位，宣称同分下比 Opus xhigh 便宜 54%，另有一个网页压缩到 129.8× 小的 browse 模块。

**适用场景**: 日常使用 Claude Code、Codex、Gemini CLI 的个人开发者和团队，长会话账单高、上下文被测试日志和 JSON 塞满的场景；也适合把 Agent 接入 CI、需要反复看构建输出的团队。

**竞品对比**: 跟微软 LLMLingua 这类提示压缩、以及 Claude Code 自带的 /compact 比，最大区别是它不在提示词上做压缩，而是压输出风格和工具返回值；Auto 的模型路由则和 OpenRouter 一类路由服务有重叠。

**成熟度**: 4.0.0 已发布、Apache-2.0、一条 npx 装完，Star 是长期堆积的（今日只涨 227）；但关键收益数字基本是自测，外部只有 JetBrains 一个 p=0.82 的 A/B（输出 token 只降 8.5%），上生产前建议自己跑基准。

**趋势信号**: 4.0 一次放出六个模块加免费的 Caveman Code 客户端，再叠加 Adobe 论文引用和 JetBrains 博客的 A/B 结果，把它从“梗项目”变成了省钱工具，冲上 Hacker News 和 GitHub Trending 第一。

### [Tencent/LoopForge](https://github.com/Tencent/LoopForge)

 `Go` ⭐ +33 今日新增 · 1,009 总星数

> 腾讯开源的私有化部署平台，把 CodeBuddy、Codex、Claude Code 等 10 种编码 agent CLI 编排成带人工审批节点的可复用 SOP，解决 agent 交付不可重复、无人把关的问题。

**亮点**

**核心功能**

- SOP 引擎按顺序跑四类节点：Agent、脚本、人工审批门、子 SOP，每个节点在独立 Docker 沙箱里执行，可从任意节点重试或重新跑

**适用场景**: 5-20 人研发团队的技术负责人或平台工程师，想用 coding agent 批量交付需求，但不能把代码发到 SaaS、且要求每次改动都走评审签字和留痕，于是自建一套内网环境。

**竞品对比**: 对标 OpenHands、Devin、GitHub Copilot coding agent 以及 Vibe Kanban / Conductor 这类多 agent 看板。最大差异是它不自研 agent 内核，而是当 10 种 CLI 之上的工作流与审批层，并且完全私有化部署。

**成熟度**: 腾讯开源、MIT 许可、有 CI 和一键 Docker 安装脚本，但 1k star 量级、发布不久，属于早期可用，SOP 格式和 API 可能还会变。

**趋势信号**: 2025 年终端类编码 agent（Claude Code、Codex CLI、CodeBuddy、Kimi Code）集中爆发却都缺团队级编排与审计，腾讯此时把内部多 agent 交付流程开源，正好卡在“agent 上生产”的需求窗口。

### [ag-ui-protocol/ag-ui](https://github.com/ag-ui-protocol/ag-ui)

 `TypeScript` ⭐ +9 今日新增 · 17,456 总星数

> AG-UI 是一套开放的事件协议，把 Agent 后端和前端界面之间的通信标准化，补上 MCP（给 Agent 工具）、A2A（Agent 之间对话）之外用户交互这一环。

**亮点**

- 把自己明确定位成协议栈第三层，与 MCP、A2A 互补而不是竞争；再用 LangChain、CrewAI、微软 Agent Framework、Google ADK、AWS Strands 等一方的适配器铺开生态，一次协议改动就能让所有框架的前端复用。
- 只规定事件语义，不规定传输、不规定 UI 库、不规定模型，把灵活性交给中间件。代价是事件匹配逻辑要容忍格式差异，换来的是几乎任意栈都能接入。

**核心功能**

- 定义了约 16 种标准事件类型，包括文本增量、工具调用开始/结束、状态快照、状态增量补丁和运行结束等。Agent 后端按这些类型发事件，前端只解析这一套，不用为每个框架写一遍渲染逻辑。
- 中间件层做“宽松事件匹配”：传输层不锁定，SSE、WebSocket、webhook 都能运行；对不完全符合规范的旧事件格式也做兼容映射，这样接一个已有的 Agent 后端不用重写协议。
- 共享状态用增量补丁同步，不是每轮把整个 state 全量推给前端；前端工具（浏览器里的函数）可以注册成 Agent 可调用的工具，人在回路（human-in-the-loop）靠事件流暂停、等用户确认再继续。

**适用场景**: 面向正在做 AI 产品前端的团队，比如用 CopilotKit、LangGraph 或 Google ADK 搭内置助手的产品工程师。典型场景是：后端已有 LangChain/CrewAI 的 Agent，但要在 React 界面里流式显示回答、同步表单状态、让用户点确认后 Agent 才执行下一步。

**竞品对比**: 同领域有 Vercel AI SDK 的 Data Stream Protocol/useChat、OpenAI 的 Assistants 流式接口，以及 CopilotKit 自己的 runtime。最大区别：那几个要么绑某个 UI 库，要么绑某家模型厂商，AG-UI 是不依赖框架和厂商的开放协议，且已有 10 多个 Agent 框架的一方适配。

**成熟度**: 脚手架（create-ag-ui-app）、文档站和 Dojo 在线演示都齐全，10 多个框架已集成，但核心包版本仍在 0.x，规范还有改动空间，大规模生产前建议锁定版本。

**趋势信号**: 2025 年 MCP 管工具、A2A 管多 Agent 通信相继被广泛采用后，只剩“Agent 怎么接前端”没有标准，AG-UI 正好占住这个位置，加上 CopilotKit 拉来 LangChain、Google ADK、微软 Agent Framework 一起做集成，star 数才会累积到 1.7 万。

### [GoogleChrome/modern-web-guidance-src](https://github.com/GoogleChrome/modern-web-guidance-src)

 `TypeScript` ⭐ +1,231 今日新增 · 6,288 总星数

> Google 联合微软、Mozilla、MDN 把 250 个现代 Web 特性的正确写法做成 coding agent 的 skill，通过 CLI 按需注入上下文、扫描旧代码，防止 AI 生成过时的前端代码。

**亮点**

- 跨厂商共管：Chrome、Edge、Firefox、MDN 四家一起署名，兼容性数据不是单一浏览器视角，能避免 agent 只推 Chrome-only API，这点是别家 skill 做不到的
- 把“指南本身”当产品做：内容密度和 token 预算比覆盖面更重要，用评测结果决定删哪条，而不是无脑堆文档

**核心功能**

- 把 250 个现代 Web 特性（其中 140 条是 CSS，从 container queries、oklch 到 Popover API、scheduler.yield）写成 agent 可直接读的 Markdown skill 文件，CLI 的 search/retrieve 只把命中的那一条塞进上下文窗口，而不是整包文档
- 用 eval 打分来裁剪内容：跑模型评测看哪些是模型本来就会的“最大公约数”内容，删掉只留模型常写错的部分，目的是压 token；README 挂了公开的 eval dashboard
- 提供 legacy-scan 子命令扫描存量代码库里被原生能力取代的旧写法（旧式 modal、重 polyfill、手写滚动动画等），给出替换建议

**适用场景**: 前端团队和平台组在用 Claude Code、Cursor、Copilot 生成组件时，发现 AI 老写 jQuery 式 DOM 操作、手搓 dialog、上重 polyfill；用 npx 装一次 skill，再对老项目跑 legacy-scan 做技术债清理。

**竞品对比**: 和 caniuse、MDN BCD、WebDX Baseline 比，那些是给人看的兼容性数据，这个是给 agent 看的“怎么写 + 怎么写回退”；和 Context7 这类抓文档喂模型的 MCP 比，它不抓原文，而是人工策展、按 eval 压缩过的短指南，还多一个扫存量代码的 legacy-scan。

**成熟度**: 早期项目，仓库刚开源、指南格式和 CLI 参数都可能变，但有 GOVERNANCE.md 和四家浏览器厂商站台，不是个人玩具。

**趋势信号**: 2025 下半年 agent skills 成了新的分发形态（Claude Skills 带起来的那套），加上 Claude Code / Cursor 大面积用于前端开发，Google 抢先把 Web 平台最佳实践做成 skill 占位，跨浏览器联合署名又加了话题度。

### [alibaba/open-code-review](https://github.com/alibaba/open-code-review)

 `Go` ⭐ +893 今日新增 · 51,566 总星数

> 阿里把内部跑了两年的 AI 代码审查工具开源。确定性流水线负责选文件、配规则、定位行号，LLM Agent 只做动态判断，解决通用 Agent 审查时漏文件、行号飘、质量不稳的问题。

**亮点**

- 明确取舍：精度优先于召回。同等模型下 Precision 和 F1 高于 Claude Code，token 只花约 1/9，但故意接受更低的 Recall。这是个诚实的产品决策，不是样样都要。
- 公开了 AACR-Bench：50 个开源仓库、200 个真实 PR、10 种语言、1505 条人工标注问题，由 80 多名资深工程师交叉验证。代码审查类工具很少有这种规模的公开评测集。

**核心功能**

- 把相关文件打成 bundle（如中英文 properties 文件捆一起），每个 bundle 起一个独立上下文的子 Agent 并发跑。大 changeset 不会因上下文塞满而漏审，这是纯语言驱动的 Agent 做不到的。
- 用模板引擎做规则匹配，按文件特征挑对应规则集（NPE、线程安全、XSS、SQL 注入），而不是把所有规则一股脑塞进 prompt，减少噪声。
- 评论的定位和反思拆成独立模块：模型先说问题，再由专门的模块校正这条评论该挂在哪个文件哪一行，压住行号漂移。

**适用场景**: 适合把 AI 审查接进 GitHub/GitLab PR 流程或 CI 的研发团队，尤其是改动量大、人工 review 排不过来的中大型项目。审计陌生代码库时可以用 ocr scan 整文件扫，不依赖 diff。

**竞品对比**: 对标的是 Claude Code + Skills 这类通用 Agent，以及 CodeRabbit、Qodo 这类商业审查工具。最大差异是它不靠 prompt 硬扛整个流程，选文件、分组、定位这些必须准的环节全用确定性代码锁死，模型只负责判断。

**成熟度**: 内部在阿里跑了两年、服务数万开发者，工程上算经过验证；但开源版很新，API 和规则集可能还会变，接入前建议先在小仓库试。

**趋势信号**: Claude Code、Codex、Cursor 这批 Agent 工具正热，阿里挑这个时候把内部工具连同公开基准一起放出，正好卡在『AI 做代码审查』从尝鲜走向工程化的节点上。

- 从读取 checkpoint、分词到调用 GPU kernel 全部在 Zig 二进制内完成，启动服务不需要 Python 运行时，也不需要 MLX；在 Linux 上只需一个 tarball 和 glibc 2.28
- 同一套代码支持 Metal、CUDA 13 和 Vulkan 三套后端。CUDA 版在启动时检查驱动版本，低于 R580 就直接拒绝启动，以免加载 kernel 后才崩溃
- 提供四套兼容接口：OpenAI 的 chat/completions、completions、Responses，以及 Anthropic Messages；--parallel 会按显存和引擎容量自动决定能同时运行几路（比如 CUDA 上显示“8 streams at once”），超出容量的请求进入队列，取消排队中的请求会把它移出队列
- 实验特性 Living Weights：把对话中学到的事实直接写回 checkpoint 的权重文件，不走 RAG 或上下文注入；代价是会互相干扰，记忆多了会衰减，Mac 上解码也会变慢

**适用场景**: 适合想在 Mac 或单张 NVIDIA 卡（包括 GB10 这类 ARM 机器）上本地运行小模型的人，例如用 Qwen3.5-2B 4bit 启动服务，再用 curl 按 OpenAI 格式调用。也适合不想在服务器上维护 Python 环境的团队，企业版 Starlight 则面向需要统一端点、账号和计费的组织。

**竞品对比**: 和 llama.cpp、Ollama、MLX 同场竞争。最大差异是不依赖 Python，并且一套代码覆盖 Metal/CUDA/Vulkan；但 llama.cpp 有 GGUF 生态和大量模型适配，TensorFold 目前只验证了 Qwen3.5-2B 这类 4bit 小模型。

**成熟度**: 版本 1.2.9，有 Homebrew 包和桌面 App，但 App 还是 beta 9，企业版自认“新”，实验特性也明确标注，属于能用的早期阶段，API 可能变动。

**趋势信号**: 1.2.9 发版、加入 GB10/aarch64 Linux 支持，再加上“用 Zig 手写推理引擎”和公开的 agent 协作雷达，在本地部署和 Zig 圈子里被转发讨论。

## 趋势观察

这波项目讲的是同一件事：AI 编程 agent 开始补工程化短板。以前比谁生成得快，现在比谁少闯祸。人工审阅界面、腾讯的审批 SOP、阿里的代码审查流水线，都在给 agent 加关卡。Google 联合微软、Mozilla、MDN 做 Web 特性 skill，是在治 AI 写旧前端代码的毛病。Chrome DevTools 官方 MCP 让 agent 直接看控制台和网络请求，说明工具链正从“猜”转向“实测”。AG-UI 补上 Agent 与前端交互协议，MCP、A2A 之后，标准层在拼完整。Univer 改叫 AI office SDK，Qwen 做终端代理并打通 IM，TensorFold 用 Zig 跑本地推理，都是同一个方向：AI 能力要嵌进真实工作流，还要能私有化、低成本。连“穴居人腔省 token”也在提醒，token 成本仍是落地硬约束。开发者生态正在从单点神器转向可编排、可审计、可替换的流水线。官方下场和协议标准化会加速洗牌。小团队的机会在垂直场景和体验层，不在重复造一个通用 agent。
