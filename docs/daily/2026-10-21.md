### [MadsLorentzen/ai-job-search](https://github.com/MadsLorentzen/ai-job-search)

 `Python` ⭐ +3,861 今日新增 · 61,146 总星数

> 一个跑在 Claude Code 上的求职框架：抓招聘网站、按匹配度打分、用 LaTeX 生成定制简历和求职信、准备面试。作者被裁后用它投了 69 份，拿到 offer。

**亮点**

- 把求职材料当代码管：简历模板、profile、求职信都在 git 里，每次投递从同一份事实来源重新生成，而不是让模型现场编
- 核心工作流（自我画像、匹配评估、写作批改）和招聘门户 skill 分层设计，作者明说门户搜索是丹麦专用的可替换外壳，其他国家的分叉只换这一层

**核心功能**

- 每个招聘门户做成一个 skill 目录，自带 Bun 写的 CLI（Jobindex、Jobnet、LinkedIn、Freehire 等）；install 脚本靠扫描目录自动发现并 bun install，不要手写清单，新加门户复制一个目录就行
- drafter-reviewer 双 agent 流水线：一个 agent 按岗位写简历和求职信，另一个 agent 按评估标准逐条批改，改完再出终稿，避免一次成稿
- 简历和求职信都是 LaTeX 模板编译：CV 用 lualatex（pdflatex 在装了 fontawesome5 的新版 MiKTeX 上会炸），求职信用 xelatex（cover.cls 依赖 fontspec），再用 pypdf 或 pdftotext 做 ATS 可解析性检查，两个都没有就降级成关键词人工看
- /rank 批量打分：一次抓回来几十个岗位时，先按匹配框架统一打分排序，再决定投哪几个

**适用场景**: 找工作的个人，尤其技术岗。把仓库 fork 成私有库、填好 profile 后，每周跑一次 /scrape 和 /apply，替代手工刷招聘网站和熬夜写求职信。

**竞品对比**: 和 Rezi、Teal、Simplify 这类在线简历和自动投递工具比，它不收订阅费、不上传简历到别人服务器，全跑在本地 Claude Code 里；代价是得自己装 LaTeX 和 Bun，且抓取的门户主要覆盖丹麦。

**成熟度**: 个人项目，无版本号，但有 CI、安装脚本和详细 SETUP 文档；作者自用拿到 offer 算真实验证，不过 /setup 会把个人信息写进 tracked 文件，必须转私有仓库再用。

**趋势信号**: Claude Code 的 skill 和斜杠命令机制刚被大量开发者摸索，加上作者“被裁后靠这套东西上岸”的经历在 LinkedIn 和 YouTube 上传开，直接引爆传播。

### [cloudflare/security-audit-skill](https://github.com/cloudflare/security-audit-skill)

 `JavaScript` ⭐ +1,712 今日新增 · 34,556 总星数

> Cloudflare 开源的编码 Agent 技能包，把 Claude Code 之类工具变成分阶段安全审计员，用多个互相隔离的 Agent 分别做侦察、狩猎、反驳验证，输出可机器校验的漏洞清单。

**亮点**

- 找出漏洞的 Agent 和验证漏洞的 Agent 永远不是同一个，验证者任务是去推翻候选结论——这是对抗 LLM 编造漏洞幻觉最直接的做法，比调提示词让对方'更严谨'管用
- 用 coverage-ledger.json 做覆盖账本：不是'扫一遍完事'，而是把代码拆成单元登记、由 critic 找漏掉的单元，官方自己跑测试的结论是单次运行只找到反复运行总漏洞量的约一半
- 没有 OS 级沙箱（禁网、白名单环境、资源限额、只写 scratch 目录）就不执行被测代码，结论最多停在 needs_validation，把'能跑但危险'和'已验证'分开

**核心功能**

- 六阶段流水线：先出 architecture.md 和 coverage-ledger.json 划清信任边界和已覆盖单元，再按 ledger 单元派独立 hunter 去找洞，可疑点交给全新 verifier 专门证伪，最后写 findings.json
- 两个零依赖 Node 校验脚本（validate-coverage-ledger.cjs / validate-findings.cjs）配 report-schema.json，强制每条结论只能是 confirmed / needs_validation / rejected 三态，confirmed 必须有完整源码调用链，needs_validation 必须写明一条没解决的具体事实且不许打严重等级
- 按攻击面拆分提示词库：MEMORY-SAFETY-AND-BINARY、AI-AND-LLM（提示注入、工具调用、输出处理）、WEB-PROTOCOL-AND-AUTH（HTTP 请求framing、缓存、认证协议）、CLIENT-SIDE（DOM 注入、postMessage 信任、原型污染）、SUPPLY-CHAIN、CLOUD-AND-DEPLOYMENT 等十余份，按目标类型挑着用
- 多次运行是叠加的：读上一轮 ledger 和 findings，只补未覆盖单元、重验改过的源码，不把旧结论或没解决的线索算成已覆盖

**适用场景**: 安全工程师或开发团队在 CI 前对某个仓库做一轮 AI 辅助审计，产出一份带源码证据的 REPORT.md 交给评审；也适合甲方安全团队在没有 CodeQL 查询规则的情况下，快速摸清陌生服务（内部 RPC、多租户 SaaS、LLM Agent 应用）的攻击面

**竞品对比**: 和 Semgrep、CodeQL、Snyk 那类规则/查询驱动的 SAST 不同，它不写规则，靠 LLM 按攻击面提示词自主寻找，覆盖面靠 ledger 和多轮迭代而非规则库；相比 XBOW 这类自动化渗透 Agent，它只做源码静态审计，不真打目标。最大差异是那个'新鲜 Agent 独立证伪 + 结构化三态输出'的去幻觉设计，常见 LLM 代码审计工具基本只输出一段自然语言。

**成熟度**: 早期但底子硬：无版本号、以 Agent skill 形式分发，文档和校验器测试齐全，来自 Cloudflare 内部已在 fleet 规模使用的 harness，不过作者自己说单次扫描只覆盖约一半问题，适合当线索生成器而不是验收工具。

**趋势信号**: 由 Cloudflare 博客《Build your own vulnerability harness》带火，撞上 Claude Code / skills.sh 这类 Agent skill 生态爆发，加上各家都在试 AI 自动挖洞，大家想直接抄 Cloudflare 内部那套多 Agent 审计流水线。

### [stablyai/orca](https://github.com/stablyai/orca)

 `TypeScript` ⭐ +1,565 今日新增 · 100,016 总星数

> 多 agent 调度台：把 Claude Code、Codex 等终端 agent 分到各自 git worktree 并行跑，桌面加手机统一盯进度，避免互相踩文件。

**亮点**

- 隔离用 git worktree，不用容器，所以 agent 产出天然就是一个可 diff、可合并的分支，省掉从容器里往外搬代码这一步
- 手机端不是简单查看器，agent 跑完会推送通知，人可以直接在手机上追加指令，把'人离开电脑就卡住'这个断点补上

**核心功能**

- 同一个 prompt 可以分发给最多 5 个 agent，每个 agent 独占一个 git worktree，结果并排对比后只合并胜出的那份
- 内嵌终端标榜对标 Ghostty，用 WebGL 渲染，支持无限分屏，滚动历史在 App 重启后仍然保留
- Design Mode 在真实 Chromium 窗口里点选任意 UI 元素，自动抓出该元素的 HTML、CSS 和裁切截图，直接拼进 agent 的 prompt
- 自带 orca CLI，暴露 worktree create、snapshot、click、fill 等命令，让 agent 反过来脚本化操作 IDE 本身和桌面 UI

**适用场景**: 适合已经同时订阅 Claude Code 和 Codex、一天开好几个 agent 的独立开发者和小团队；也适合笔记本性能不够、想用 SSH 把 agent 丢到远程大机器上跑，再用手机看结果的人。

**竞品对比**: 和 Conductor、Crystal、claude-squad 这类多 agent 编排工具同类，也和 Cursor、Windsurf 这种内置单 agent 的 IDE 有交叉。最大区别是不自带模型，直接用你自己的 Claude/Codex 订阅，且把桌面 GUI、手机端、SSH 远程和 GitHub/Linear 任务面板做进一个壳里。

**成熟度**: 迭代很快、自称每日发版，功能列表常年滞后于 changelog，iOS 版已上架 App Store，但版本仍在 1.0 之前的快速变动期。

**趋势信号**: Claude Code、Codex CLI 这类终端 agent 今年成了主流用法，大家开始同时开好几个，'谁来管这一堆 agent'变成新痛点，Orca 正好卡在这个位置上，加上移动端和 Design Mode 这类差异化功能刚上线。

### [anomalyco/opencode](https://github.com/anomalyco/opencode)

 `TypeScript` ⭐ +1,240 今日新增 · 219,121 总星数

> OpenCode 是开源的终端 AI 编码 agent，能在本地读写代码、跑命令、改文件。它不绑定某一家模型厂商，适合想要 Claude Code 那套体验但要求开源、可换模型的人。

**亮点**

- 把 agent 做成 server 而不是一个单体 CLI，前端（TUI / Tauri 桌面端 / Web）全部解耦。好处是会话状态在后端，多端能接同一个任务，也方便以后做远程或团队共享
- 默认开 LSP 而不是只靠模型自己读文件，等于把编译器的反馈直接喂给 agent，减少改完跑不通再来一轮的来回

**核心功能**

- 核心 agent 跑在一个本地 server 进程里，TUI、桌面 App、Web 都只是通过 HTTP 连进来的客户端，所以同一个会话可以多端同时接、也能生成链接分享给别人看
- 内置 build 和 plan 两个 agent，Tab 键切换。plan 是只读的：默认拒绝改文件、跑 bash 前要先问，用来先摸清陌生代码库再动手；复杂搜索交给 @general 子 agent
- 接了 LSP（语言服务器，就是 IDE 里给你标红报错的那个东西），agent 改完代码能直接读到类型错误和诊断结果，不用靠猜自己改对没有
- 模型无关：通过 Models.dev 的 provider 表接入 Anthropic、OpenAI、Google 以及本地模型，换模型只改配置
- 分发渠道铺得很全：curl 脚本、npm/bun/pnpm、Homebrew、pacman、mise、Nix 都能装，安装脚本按 XDG 规范优先选目录

**适用场景**: 习惯在终端里干活的开发者，尤其是已经在用 Claude Code / Codex CLI 但想换模型、或公司不允许把代码发到外部 API 的团队。典型流程是：进项目目录起 opencode，用 plan agent 读代码出方案，切 build agent 让它改。

**竞品对比**: 直接对标 Claude Code、OpenAI Codex CLI 和 Gemini CLI，最大差别是厂商中立——上面几个只能用自己的模型。相比 Aider 这类老牌开源工具，它的形态更接近完整的 agent 产品（TUI + 桌面端 + 子 agent + LSP），而不只是一个 CLI 补丁工具。

**成熟度**: 已过 0.1.x 进入 v2，有多语言文档、Discord 社区和 Homebrew/npm/pacman 多渠道分发，桌面端还是 beta，迭代很快、配置和 API 仍可能变。

**趋势信号**: Claude Code 带火了终端 agent 这个形态，同时很多人对它锁死 Anthropic 模型和闭源不满；OpenCode v2 发布加上桌面端 beta，正好接住这波'要开源、要能换模型'的迁移需求。

### [DietrichGebert/ponytail](https://github.com/DietrichGebert/ponytail)

 `JavaScript` ⭐ +1,208 今日新增 · 170,081 总星数

> 给 AI 编码 agent 装一套「最懒资深工程师」的行为规则：先翻仓库里已有的东西，只写必要的代码，再配审查、审计命令和成本面板。对上了现在 agent 狂造轮子、token 烧钱的痛点。

**亮点**

- 明确的反向取舍：省 token 不是目标，「只写任务需要的、但校验/错误处理/安全/无障碍一个都不许砍」才是。benchmark 里代码少了 53%，六个安全任务（SQL 注入、路径穿越、伪造 token、限流等）30 次跑全过
- 把「代码风格」做成可量化指标——复用率、测试覆盖率、每轮成本直接摆在提示框上方，让「少写」从一句口号变成能看见的数字，这点比单纯写 CLAUDE.md 规则文件更狠

**核心功能**

- 分发形式是 Agent Skill：一段注入 agent 上下文的行为规则加几个斜杠命令（/ponytail-review、/ponytail-audit），npm 装一次，宣称兼容 20 个 agent（Claude Code、Cursor 等），不碰模型也不走额外 API
- 强制「先搜后写」：动手前先扫仓库已有的组件和工具函数。README 的例子是要个日期选择器——不加库不手写 335 行日历，而是复用仓库已有的 Input 组件加浏览器原生 type=date，10 行搞定
- 审查时读「改动牵连到的文件」而不只是 diff：benchmark 里抓到一个重命名字段导致未修改的 src/routes/feed.js 里 Atom feed 每次请求都崩；audit 则先画入口点、数据流、预期负载，再给修复优先级排序
- Claude Code 里有一条常驻状态栏（band），显示本轮花费、token 数、agent 耗时、复用率（复用旧代码 vs 新写）以及最后一次改动后测试是否通过，数据从会话 hook 里取

**适用场景**: 日常用 Claude Code / Cursor 写业务代码的工程师，尤其是接手老仓库、前端组件库已经很全的团队。典型场景：让 agent 加个表单控件、改个字段名，结果它装了一堆依赖、写了三百行；或者 code review 时只盯 diff，漏掉被改坏的调用方。

**竞品对比**: 对手是手写的 CLAUDE.md / .cursorrules 规则文件和各类 prompt 模板。差别在于 Ponytail 把规则打包成带斜杠命令、带 benchmark 数据、带成本面板的成品，而不是让你自己摸索措辞；代价是它绑定具体 agent 的 skill 机制，换工具就得看兼容性。

**成熟度**: 版本到 5.3，迭代很快（4.13 到 5 是大重写），有 npm 包、多语言 README、benchmark 目录和 MIT 协议，属于「能用、但效果高度依赖模型版本」，且性能数字是作者自测自评，需自行验证。

**趋势信号**: 踩在两点上：一是 Claude Code 的 Agent Skills 刚成为主流分发形式，生态在爆发；二是大家普遍抱怨 AI agent 过度生成代码、乱装依赖、token 账单失控，Ponytail 5 刚好在这个时间点放出重写版和一整套对比数据。

### [Comfy-Org/ComfyUI](https://github.com/Comfy-Org/ComfyUI)

 `Python` ⭐ +1,206 今日新增 · 140,937 总星数

> ComfyUI 是本地跑扩散模型的节点式引擎，把生图、生视频、3D、音频拆成可连线的图，新模型发布当天基本就能用，最近因为一批新开源模型（Flux.2、Wan 2.2、Qwen Image 等）集中上线而持续涨星。

**亮点**

- 把"引擎"和"界面"彻底分开：核心是个无头后端，前端只是其中一个客户端，所以同一套工作流能本地跑、桌面端跑、也能上云跑
- 新模型适配速度是它的护城河——社区和官方在模型权重放出当天就补上节点，用户不用等官方 SDK

**核心功能**

- 异步权重流式加载：把大模型的权重分块从内存搬进显存，边算边搬，4GB 显存 + 8GB 内存就能跑几十 GB 的开源大模型，代价是速度换显存
- 部分图重执行 + 节点级缓存：改一个节点只重算受影响的子图，前面的采样结果直接复用，调参时不用整条流程从头跑
- 节点图即 JSON：工作流存成 JSON，同一份图既能拖拽编辑，也能通过本地 HTTP API 提交给后端批量跑，还能用 App Mode 把复杂图收成几个输入框给非技术用户
- 原生支持量化模型和模型分离加载（diffusion 模型 / VAE / 文本编码器 / LoRA / ControlNet 分开挂），显存不够时自动 offload 到内存

**适用场景**: AI 绘画和视频的工作室、独立创作者、以及要把生成能力接进产品流水线的工程团队。典型流程是设计师在节点图里搭好一套出图管线，再用 API 或 App Mode 交给运营或客户端批量调用。

**竞品对比**: 和 Automatic1111 WebUI、Fooocus 比，那两者是表单式的固定流程，只能调参数不能改结构；ComfyUI 是图编程，代价是学习曲线陡。和云端闭源的 Midjourney、Runway 比，最大差异是本地离线、模型权重完全自己掌控。

**成熟度**: 生产可用：版本号已到 0.7.x，按周发版、双周出稳定版，有桌面端和付费云服务，Discord 社区体量大，但 master 分支的提交会破坏第三方自定义节点。

**趋势信号**: 近期 Flux.2、Qwen Image、Wan 2.2、HunyuanVideo 1.5、Nano Banana 等一批新模型密集发布，ComfyUI 每次都是首批支持，加上仓库迁到 Comfy-Org 组织账号并推桌面端和云服务，把新模型带来的流量接住了。

 `Python` ⭐ +802 今日新增 · 130,489 总星数

> 把代码、文档、SQL schema、配置和 PDF 一起解析成一张可查询的知识图谱，用 /graphify 技能装在 Claude Code、Cursor 等 AI 编码助手里，让 Agent 查图而不是逐文件 grep。

**亮点**

**核心功能**

- 代码部分用 tree-sitter 做 AST 解析，纯本地、不调用 LLM、确定性输出，因此索引代码不花 token；文档、PDF、图片、视频才走模型做语义抽取

- graph.json 里写入 graph.schema_version 和 graphify_version，让下游集成能识别格式不兼容的版本变化

**适用场景**: 接手几十万行陌生仓库的工程师，用 Claude Code / Cursor 提问时不想让 Agent 一个文件一个文件读；也适合需要把 SQL 表结构和后端代码对上号的数据/后端团队，以及要给“这个结论从哪来的”留证据的审计类场景。

**竞品对比**: 对标 Sourcegraph/Cursor 的代码索引（embedding 向量检索）和 aider 的 repo map（tree-sitter + PageRank 摘要），也抢 Serena 这类 LSP 符号检索 MCP 的活。最大差异是不建向量库、边带可信度标签，并且把 PDF、SQL schema、配置一起塞进同一张图，而不只是源码。

**趋势信号**: AAAI 2026 中稿消息、arXiv 论文、HF 权重和 BTC/USDT 在线 demo 一起放出，赶上“金融时序基础模型”这波热度。

### [headroomlabs-ai/headroom](https://github.com/headroomlabs-ai/headroom)

 `Python` ⭐ +549 今日新增 · 76,849 总星数

> 给 AI Agent 做本地上下文压缩层：日志、JSON、代码、RAG 块按类型分别压缩，原文可回查，编码 Agent 省约 20%、JSON 省 60-95% token，答案不变。

**亮点**

- 把“省 token”和“KV 缓存命中”放在一起算账：多数压缩工具只看压完多少 token，CacheAligner 则单独处理会打乱缓存前缀的内容，这是少见的工程细节
- CodeCompressor 用 AST 而不是文本截断来压缩代码，保留语法结构和关键符号，所以模型读压缩后的代码仍能理解逻辑

**核心功能**

- ContentRouter 先判断内容类型再分发：JSON 交给 SmartCrusher 做结构化裁剪，源码交给 CodeCompressor 按 AST 删掉不影响语义的结构，散文交给自研小模型 Kompress-v2-base（已放上 HuggingFace），不再对所有内容采用同一种统一压缩方式
- CCR 可逆压缩：压缩后原文缓存在本地，同时给模型暴露 headroom_retrieve 工具，模型需要细节时能取回全文；演示里 10144 token 的日志压到 1260 token，第 67 行的 FATAL 行仍逐字节保留
- CacheAligner 专门标记会让 provider KV 缓存前缀失效的易变内容（时间戳、随机 ID 等），只做标记不重写 prompt，避免省下输入 token，却因缓存 miss 付更多钱
- 三种接入方式：Python/TS 的 compress\(messages\) 库、headroom proxy 透明代理（零改代码）、以及 headroom_compress/retrieve/stats 三个 MCP 工具，另外可用 headroom wrap 一条命令把 claude/codex/cursor/aider 等十几个 Agent 挂上去

**适用场景**: 主要面向用 Claude Code、Cursor、Codex 长时间写代码的开发者或团队：一次会话塞进几十个工具输出、CI 日志和文件内容，上下文窗口和账单都顶不住。也适合 SRE 排障时把大段日志喂给模型、以及 RAG 检索块太长需要先压缩的场景。

**竞品对比**: 对比微软 LLMLingua / LLMLingua-2、Selective Context 这类通用 prompt 压缩：那些基本是对所有文本做 token 剪枝，压缩不可逆，也不管 provider 的 KV 缓存。Headroom 的差异在于内容类型路由、用 AST 做代码压缩、可回退检索，以及跨 Claude/Codex/Gemini/Grok 的共享记忆。

**成熟度**: 版本未到 1.0，但 CI、文档站、HF 模型卡和可复现基准脚本都齐；压缩毕竟会改写输入，建议先用在日志、JSON 这种能 retrieve 回原文的场景。

**趋势信号**: 编码 Agent 的长会话普遍遇到上下文窗口和 token 账单上限，MCP 生态同期爆发；项目此时放出 Kompress-v2-base 模型，并登上 Trendshift 日榜第一，借势推广。

### [vllm-project/vllm](https://github.com/vllm-project/vllm)

 `Python` ⭐ +128 今日新增 · 94,516 总星数

> vLLM 是一个开源 LLM 推理和服务引擎，核心是 PagedAttention 显存管理加连续批处理，让同样的 GPU 跑出更高并发吞吐。现在开源大模型密集发布，它是新模型上线时最常被选中的部署后端。

**亮点**

- 把 prefill 和 decode 拆到不同机器上跑（disaggregated prefill/decode）：前者吃算力、后者吃显存带宽，混在一块互相拖累，拆开后各自用最合适的卡型和并行策略
- 用一个统一的 OpenAI 兼容 server 把调度、并行（张量/流水线/数据/专家/上下文）、多 LoRA、结构化输出（xgrammar/guidance）、工具调用解析全包了，用户换来换去只改模型名

**核心功能**

- PagedAttention：把 KV cache 切成固定大小的块，像操作系统管虚拟内存那样按需分配、按块回收，显存碎片极少，同卡能塞下更多并发请求
- 连续批处理 + 分块预填充 + 前缀缓存：新请求不必等整批跑完就能插进来；长 prompt 拆段和正在解码的请求混着算；相同的系统提示词只做一次 prefill
- 投机解码支持 n-gram、suffix、EAGLE、DFlash：先让便宜的方式猜几个 token，再让大模型一次并行验证，输出结果不变但解码步数减少
- 内核不绑死一家：FlashAttention、FlashInfer、TRTLLM-GEN、FlashMLA、Triton 都能替换，GEMM/MoE 用 CUTLASS 手写，并用 torch.compile 做图级变换自动生成 kernel
- 量化覆盖 FP8、MXFP8/MXFP4、NVFP4、INT8/INT4、GPTQ/AWQ、GGUF，同一套服务代码可以在 NVIDIA、AMD、Intel GPU 和 CPU 上跑，昇腾、TPU、Gaudi、Apple Silicon 走插件后端

**适用场景**: 需要在自有 GPU 上部署开源模型的团队：AI 应用公司把 Qwen、Llama、DeepSeek 挂成 OpenAI 兼容 API 给前端调用；模型厂做 RLHF 采样和批量评测；云厂商和推理服务商按 token 卖算力。

**竞品对比**: 主要对手是 SGLang（靠 RadixAttention 做前缀复用，复杂 agent 负载上常更快）、TensorRT-LLM（NVIDIA 自家极致优化但只吃 N 卡、上手重）、Ollama/llama.cpp（本地单机易用但吞吐差一个量级）。vLLM 的差异点是模型覆盖（200+ 架构）和硬件覆盖最广，几乎是新模型新芯片的第一站。

**成熟度**: 生产可用，2000+ 贡献者、每几天一个 release，是很多公司的默认推理后端；但版本号还在 0.x，小版本升级偶有破坏性改动，锁版本后再上生产。

**趋势信号**: DeepSeek-V3、Qwen-MoE、GPT-OSS 这类 MoE 和混合注意力模型接连放出，加上 vLLM 自己推的 v1 引擎重构和 prefill/decode 分离部署，每次有大模型开源，大家第一件事就是确认 vLLM 支不支持，star 就跟着涨。

- 配套 plugin-eval 做不调模型的静态 skill 检查（结构、引用、长度），另有 LLM 评审和蒙特卡洛重复模拟两层，作者自己标明是实验性、没和人工标注对齐
- 支持 skills-only 安装，gh skill / npx skills 直接从 GitHub 取单个技能，不 clone 仓库，也不带 agents 和 hooks

**适用场景**: 已经用 Claude Code 或 Cursor 的开发者，想给团队统一一套代码评审、测试、Python/JS 脚手架和安检的提示词资产；也适合同时用两三种编码 agent、不想维护多份配置的人。

**竞品对比**: 对标 Anthropic 官方 Claude Code 插件市场、各家 awesome-claude-code 清单，以及 superpowers、BMAD-METHOD 这类方法论仓库。最大差别是唯一同时出 7 个工具的适配版本，代价是每个工具能用的能力被砍（Pi 缺 agents、Copilot 命令变 skill）。

**成熟度**: 内容和安装脚本可以直接用，但技能评分体系还是实验性的，跨工具能力参差不齐。

**趋势信号**: Claude Code 插件市场、Codex CLI 的 plugin marketplace、Cursor 的 plugin registry 在 2025 年底扎堆出现，GitHub CLI 2.90 又内置了 gh skill，这仓库正好卡在“插件和技能要不要跨工具通用”这个讨论点上。

### [sickn33/agentic-awesome-skills](https://github.com/sickn33/agentic-awesome-skills)

 `Python` ⭐ +83 今日新增 · 48,184 总星数

> 把 2700+ 个 SKILL.md 技能包做成可搜索的本地目录，让 Claude/Codex 经 MCP 自己挑技能，并在安装前生成可审阅的计划。

**亮点**

- 产品立场很清晰：Core 不排序、不推荐技能，只负责“搜索 + 记下 Agent 选了啥 + 校验结构合法”。选择权给模型，工具不背书质量，README 里也明说结构合法不等于语义合适
- Workbench 在浏览器内存里审 stack 和 plan 文件，完全不碰你的文件系统；apply 和 recovery 标成实验性、要显式 opt-in，默认只走只读预览这条安全路径

**核心功能**

- 本地 MCP 服务把全部 2,724 条 SKILL.md 暴露给 Agent，每条都能单独搜索和读取原文，等于让模型自己翻目录，不用人去网页上扒
- compose_stack 是只读工具，在内存里校验技能 ID 和结构（上限 128 条），之后 aas stack validate 校验清单、aas stack plan 生成不可变预览文件，装之前你都能看到
- aas mcp configure 在写配置文件前先打印要改的内容并返回一个 approval digest，用户确认后才落盘
- npm 直接分发：npx agentic-awesome-skills，不用 clone 仓库也能装单个技能

**适用场景**: 用 Claude Code、Codex、Cursor、Gemini CLI 写代码的开发者。想让 Agent 拿到现成的规范做法（某框架脚手架、代码审查清单、部署流程），又不想让它随手装一堆来路不明的指令包时，先在这套目录里筛再预览计划。

**竞品对比**: 对标 awesome-claude-skills 那类纯 Markdown 清单、cursor.directory 这类规则站，以及 Smithery 这类 MCP 注册表。最大差别是它把目录做成 Agent 能直接调用的本地 MCP，并用 validate→plan 两步卡住安装，普通清单站只负责展示。

**成熟度**: 成熟度看版本号会误导——19.12.1 是目录同步版本号。核心预览路径可用、文档齐，但 apply/recovery 明确是实验性，API 可能变。

**趋势信号**: Anthropic 的 Agent Skills（SKILL.md 文件格式）在 2025 年下半年被 Claude Code、Codex、Gemini CLI、Cursor 陆续跟进，社区里散落的技能包急需一个统一目录喂给 Agent，这个项目正好卡在这个缺口上。

## 趋势观察

今天这份榜单，几乎全是 Claude Code 的外挂。有人给它套执行外壳，把上百个 agent 编成蜂群、共享记忆、跨机器协作；有人做多 agent 调度台，每个 agent 分一个 git worktree 并行跑，桌面加手机统一盯进度；有人往里塞 94 个插件、202 个 agent、2700 个技能包。共同点很清楚：模型本身不再是瓶颈，怎么管住一群 agent 才是。 第二层是省钱和省事。「最懒资深工程师」那套规则、本地上下文压缩层、把代码和 PDF 解析成知识图谱让 agent 查图而不是逐个文件 grep，治的都是同一个病：agent 狂造轮子、token 烧钱。安全审计那个项目更直接，侦察、狩猎、反驳拆成三个互相隔离的 agent，最后输出可机器校验的漏洞清单。说明大家已经不太信单个 agent 的自说自话，开始要交叉验证和成本面板。 第三层是标准之争。SKILL.md、插件包、跨 7 种编码工具的格式转换、用 MCP 让 agent 自己挑技能，都在抢「写一次、到处跑」的入口。Anthropic 官方趁 Cowork 刚上线放出 11 个岗位插件包，等于官方下场定了份样板，第三方再跟着适配。 底座也在动。OpenCode 主打不绑模型厂商，vLLM 是新模型上线时最常被选中的部署后端，ComfyUI 因为 Flux.2、Wan 2.2、Qwen Image 这批开源模型集中发布持续涨星。开源模型一密集，部署和本地跑图的需求就跟着涨。 最能说明问题的是那个求职框架。作者被裁后自己写，投了 69 份，拿到 offer。这更像被现实逼出来的工具，不是玩具。整份榜单串起来就一句话：开发者生态正从「用 AI 写代码」，转向「搭一条能调度、能审计、能省钱的 agent 流水线」，而且官方和开源两边同时在下注。
