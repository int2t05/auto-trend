### [NVIDIA-NeMo/Switchyard](https://github.com/NVIDIA-NeMo/Switchyard)

 `Rust` ⭐ +421 今日新增 · 872 总星数

> 用 Rust 写的 LLM 流量代理，能在 OpenAI 和 Anthropic API 之间翻译，并把请求路由到不同模型后端，让编码 agent 用上任意开源模型。

**亮点**

- 协议中立：先用 switchyard-protocol 定义中间请求/响应/流类型，再分别翻译成各家 API，翻译逻辑独立成 crate，便于复用和测试。
- 库路径设计：把路由算法和 HTTP 服务解耦，宿主可以完全控制模型调用过程，适合做已有网关的插件而不是重起一个服务。

**核心功能**

- 协议翻译：在 OpenAI Chat、Anthropic Messages、OpenAI Responses 三种格式之间互转，Claude Code 等原生 Anthropic API 客户端可以直接对接 vLLM、Ollama 等 OpenAI 兼容后端。
- 路由算法：内置 LLM 分类器路由（小模型判断走弱还是强模型）、阶段路由（根据工具结果等信号直接分流）、升级路由（先弱后强，再让 judge 决定是否重试），还有随机 A/B 分流。
- 可嵌入设计：switchyard-libsy 不持有 HTTP 栈，路由算法决定目标后把模型调用交回宿主应用，能直接嵌进已有 Rust 代理或网关。

**适用场景**: 想给 Claude Code、Codex 这类编码 agent 接上开源模型的开发者，或需要多模型 A/B 测试、成本分层调度的平台团队。

**竞品对比**: 和 LiteLLM（Python 的 API 代理）相比，Switchyard 主要差异是内置 LLM 分类器和升级路由等智能策略，且 Rust 实现性能和嵌入性更好。

**成熟度**: 预 alpha 阶段，官方明确说 API 会大改，不适合生产，文档和示例刚起步。

**趋势信号**: Claude Code 等编码 agent 爆发，但默认只认 Anthropic/OpenAI API，Switchyard 正好解决把它们指向开源模型的痛点，加上 NVIDIA 背书，所以短期星数飙升。

 `Kotlin` ⭐ +40 今日新增 · 4,236 总星数

> JVM 上的 Agent 框架，用 GOAP 算法做动态规划，混合 LLM 与代码，由 Spring 创始人开发，适合企业 Java/Kotlin 集成。

**亮点**

- 规划层用非 LLM 的 GOAP 算法（游戏 AI 常用），每个动作执行后重新规划，形成 OODA 循环，能适应环境变化并发现新方案
- 作者是 Spring 创始人 Rod Johnson，框架天然面向企业级可测试性设计，单元测试和端到端测试都容易写

**核心功能**

- 用 GOAP（目标导向动作规划）替代有限状态机，系统自动组合已知动作达成新目标，不靠 LLM 推理规划
- 强类型领域模型驱动动作/目标/条件，提示词与手写代码混合时不用魔法 map，能享受 IDE 重构支持
- 基于 Spring，支持 @Agent 注解和 Kotlin DSL 两种方式定义流程，可用 Spring Boot 管理 Bean
- 规划器可插拔，默认 GOAP 还支持 Utility AI，能选不同 LLM 完成子任务，兼顾成本与隐私

**适用场景**: Java/Kotlin 后端团队构建需要 LLM 决策但核心逻辑要可控的企业应用，比如客服工单自动处理、供应链流程编排，可接入 Spring 现有事务和持久化设施。

**竞品对比**: 对比 LangChain4j 和 Spring AI，Embabel 的核心是传统 AI 规划算法而非单纯 LLM 链，同时强类型和 Spring 集成更贴合 JVM 企业习惯，不像前者偏重 Python 生态移植。

**成熟度**: 早期项目（1.5.0-SNAPSHOT），API 可能调整，但 CI、文档、质量门禁齐全，社区刚起步。

**趋势信号**: Spring 创始人 Rod Johnson 的新作品本身就自带流量，加上 JVM 上缺乏成熟的 Agent 规划框架，正好赶上企业试水 AI Agent 的热潮。
