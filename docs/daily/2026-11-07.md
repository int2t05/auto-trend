### [cloudflare/security-audit-skill](https://github.com/cloudflare/security-audit-skill)

 `JavaScript` ⭐ +2,548 今日新增 · 64,396 总星数

> 把编码 Agent 变成安全审计员：六阶段流水线加独立验证，每条漏洞结论都能追到源码和覆盖台账，主要解决 AI 审计误报多的问题。

**亮点**

- 多次跑同一个仓库是叠加的：复用上次的台账和发现，只补没覆盖的区域、重验改动过的源码，旧证据不作数。官方说法是单次大约只能找到重复跑总漏洞量的一半——这是它敢做「覆盖率」而不是「跑一遍」的前提。
- 没沙箱就不跑目标代码：缺少禁用外网、白名单环境、资源限制的 OS 级沙箱时，构建、测试、fuzzer 一律不执行，相关线索直接压成 needs_validation，用放弃召回换不误报。

**核心功能**

- 用 coverage-ledger.json 当覆盖台账，把审计拆成可分配的「单元」分给各个 hunter 子 Agent，再由 coverage critic 找漏掉的区域；台账和结论都用零依赖 Node 脚本（validate-coverage-ledger.cjs / validate-findings.cjs）做 schema 校验，不通过就返工。
- 找到漏洞的 Agent 和验证漏洞的 Agent 永远不是同一个：每个候选交给全新的 verifier 去「证伪」，结论只分三档——confirmed 要有完整源码链路和可观测结果，needs_validation 必须写清哪个事实没确认且不准标危害等级，rejected 要记下被推翻的理由。
- 按目标类型预置了十几份攻击类提示词库：内存安全/二进制、LLM 提示注入与工具滥用、HTTP 请求走私与缓存与认证、客户端 DOM 注入与原型污染、供应链与签名更新、云 IAM 与 IaC、RPC 与消息队列、资源耗尽、多租户数据隔离、桌面与本地 IPC。按目标挑类，而不是丢一套通用清单。

**适用场景**: 安全工程师和研发团队在本地或 CI 里对自有仓库做上线前审计，直接对 Claude Code、Codex 这类支持并行子 Agent 的编码 Agent 说「审计这个代码库」即可；也适合在 PR 前做一轮初筛，输出 ~/security-audit-skill/&lt;repo&gt;/run-N 下的 REPORT.md 和 findings.json。

**竞品对比**: 对手是 Semgrep/CodeQL 这类规则型 SAST 和 XBOW 这类 AI 自动化渗透。差别在于它不做模式匹配，靠子 Agent 分头狩猎 + 交叉反驳压误报，代价是慢、吃模型能力、结论偏保守（大量 needs_validation）。

**成熟度**: 刚开源不久，MIT，带单测和 JSON schema 校验、有 Cloudflare 官方博客背书，但本质是提示词工程包，效果强依赖模型和沙箱环境，还没看到外部大规模验证。

**趋势信号**: Cloudflare 发博客《Build your own vulnerability harness》公开了内部漏洞挖掘流水线，这个 skill 就是那条流水线的单仓库起点；叠上当下 AI 找漏洞（Big Sleep、XBOW、各家 security review skill）的热度，一天涨两千多星。

### [mattpocock/skills](https://github.com/mattpocock/skills)

 `Shell` ⭐ +2,070 今日新增 · 316,907 总星数

> Matt Pocock 把自己每天用的 AI 编码技能（对齐提问、共享术语表、TDD、issue 分诊）打包成可安装插件，跨 Claude Code、Codex、Copilot、Gemini CLI 复用。解决的是 Spec-Kit 类框架替你做流程、出错难改的问题。

**亮点**

- 把「共享语言」当成上下文压缩手段：术语统一后，变量名、文件名、代码结构都跟着统一，agent 思考用的 token 也少了
- 不做框架，只做可组合的小技能：每个技能单独可用，不接管你的开发流程，出问题只看一个 markdown 文件就能定位

**核心功能**

- 技能就是一堆 markdown 的 SKILL.md 文件，没有运行时和依赖；装进项目后可以直接改，改坏了也能看懂
- 用一个交互式 setup 技能采集配置：issue 跟踪器用 GitHub/GitLab/本地文件、triage 用什么标签、文档存哪，后续技能读这份配置干活
- /grill-with-docs 先让 agent 反过来盘问你需求，同时把项目黑话固化成术语表（CONTEXT.md）和 ADR，后续会话直接复用这套词，减少来回解释和 token 消耗
- /tdd 技能强制红-绿-重构：先写失败的测试，再改代码通过，给 agent 一个稳定的反馈回路

**适用场景**: 用 Claude Code、Codex、Cursor 在自己真实项目里写代码的工程师，尤其是需求容易跑偏、agent 输出啰嗦、改动缺少测试兜底的场景；也适合团队想把 issue 分诊、文档产出流程固化下来的人。

**竞品对比**: 对标 GSD、BMAD、Spec-Kit 这类 spec 驱动框架。它们替你定义整套流程，控制权在框架手里；这个仓库反过来，技能很小、可以随手改、任意组合，代价是没有强约束，靠你自己守纪律。

**成熟度**: 能用但别当稳定 API：本质是作者个人工作流的 markdown 集合，靠插件市场自动更新，接口（技能名、配置项）随时会变，文档写得清楚，社区量很大。

**趋势信号**: Claude Code、Codex、GitHub Copilot、Gemini CLI 近期都上了插件/技能市场，提示词终于能像 npm 包一样一条命令装进各家 agent，这个仓库正好踩在多端分发这件事上。

### [NVIDIA/auto-ontology](https://github.com/NVIDIA/auto-ontology)

 `Python` ⭐ +2,015 今日新增 · 9,295 总星数

> 英伟达开源的语义层框架：从企业元数据自动生成本体知识图谱，让 Agent 在生成 SQL 前先对齐业务定义、跑完再校验并给出溯源。

**亮点**

- 把本体当"编译产物"而不是提示词上下文：启动时一次性编译，问答时只做图上的确定性查询，绕开 LLM 推理表关系的不可靠环节
- 上下文层通过 MCP / CLI / API 三种方式对外，不绑自家聊天界面，任何 agent harness 都能接；同时把人工修正和查询历史回写本体，用得越多定义越准

**核心功能**

- 从数据库元数据自动生成 ontology（本体，即一张描述"有哪些指标、实体、它们怎么关联"的知识图），查询时先把自然语言里的 revenue、product、state 映射到图上的术语，再顺着关系推出该 join 哪几张表，不需要 LLM 每次现场猜表结构
- 启动时做一次"语义编译"，把跨系统冲突的定义（比如两个库里 revenue 口径不同）对齐成认证版本；运行时只查编译好的图，并用这张图校验生成的 SQL 是否用了认证定义和正确血缘，答案附带 SQL 和执行步骤
- LLM 按角色拆成多组 endpoint 配置（推理模型跑 NL-to-SQL、轻量模型只做实体抽取、embedding、rerank 各一组，未配置的自动回落到默认组），统一走 NVIDIA NIM，可切到自托管；目录、本体、向量全放一个 Postgres + pgvector 里，少一套存储

**适用场景**: 面向搭企业问数/BI 助手的数据平台团队和分析工程团队——已经在用 dbt、Cube 维护语义模型，但发现 LLM 直接 text-to-SQL 数字经常错、口径对不上。也适合想把企业数据接进 Claude Code、Cursor 等 MCP 客户端的团队。

**竞品对比**: 对标 dbt Semantic Layer、Cube、AtScale 这类手工建模的语义层，以及 Wren AI、Dataherald 这类 text-to-SQL 工具。最大差异是本体靠元数据自动生成而非人工逐条建模，且每个答案强制走定义校验和血缘溯源，而不是只把 SQL 跑出来。

**成熟度**: 早期项目，无版本号，README 明说暂不接受外部贡献、由英伟达单方维护，适合评估试用，不建议直接上生产。

**趋势信号**: MCP 正在成为 Agent 接企业数据的通用接口，同时 text-to-SQL 的准确率被普遍质疑，这个项目正好卡在"给 Agent 一个可信数据上下文层"的位置；加上英伟达品牌和 2026 年新发布带来的曝光，一天涨两千星。

### [lz4/lz4](https://github.com/lz4/lz4)

 `C` ⭐ +315 今日新增 · 12,644 总星数

> LZ4 是主打速度的无损压缩算法库，单核压缩 770 MB/s、解压 4950 MB/s，压缩比约 2.1 倍。它专治“压缩不该成为瓶颈”的场景，几乎所有数据库和文件系统都在用它。

**亮点**

- 明确的取舍策略：不追压缩比，只保证解压端接近 memcpy 速度，所以把它放在热路径上几乎不增加延迟预算——这正是它能塞进内核文件系统的原因
- 库用 BSD 2-Clause、命令行工具用 GPL-2.0-or-later，双协议分开授权，公司可以放心把 liblz4 静态链进闭源产品，而不被 CLI 的 GPL 传染

**核心功能**

- 按“块”压缩、再按“帧格式”打包成流：块格式只做纯粹的 LZ77 匹配拷贝，帧格式再加校验和、块大小、内容大小等元数据，所以解压端能跳到几乎内存拷贝的速度（4950 MB/s）
- 提供 acceleration 加速因子，运行时动态在“压缩比”和“更快”之间滑动，同一个解压器能吃所有档位；另一支 LZ4_HC 用更深的哈希链搜索换压缩比（2.717 倍），但解压速度和普通版完全一样，等于压缩慢一次、解压永远快
- 支持字典压缩：可以拿任意文件当字典（只取末尾 64 KB），配合 zstd 的字典训练器能把小文件（如 Redis 键值、日志行）的压缩比拉高一大截——这是小包场景的关键补丁

**适用场景**: 写数据库、缓存、消息队列、文件系统的工程师：Redis、Kafka、ClickHouse、ZFS、Hadoop 都内置 LZ4，用于页压缩、WAL 压缩、网络传输。也适合做日志采集和备份管道的团队，在 CPU 吃紧但磁盘/带宽贵的地方替代 gzip。

**竞品对比**: 同场竞技的是 Snappy、Zstandard、zlib、LZO。对比 Snappy，LZ4 压缩快约 48%、解压快约 3.7 倍；对比同作者的 Zstandard，zstd 压缩比高（2.896 vs 2.112）但解压只有 1570 MB/s，LZ4 解压快 3 倍。结论：要极致解压速度选 LZ4，要压缩比选 zstd。

**成熟度**: 生产就绪多年，当前 v1.11.0，被主流 Linux 发行版打包、被大量数据库和文件系统内置，API 早已稳定。

**趋势信号**: 一个十多年的老库突然单日涨 315 星，通常是 v1.11.0 新版本（README 基准已更新到该版本）被社区推送或登上技术讨论；具体触发点不明。

**趋势信号**: 近期 Windows 版可用加上 AI Agent 功能推进，赶上开发者对 Electron 编辑器性能和 AI 编程工具的双重关注。

### [microsoft/vscode](https://github.com/microsoft/vscode)

 `TypeScript` ⭐ +301 今日新增 · 195,075 总星数

> 微软官方开源的代码编辑器，跨平台、免费、插件生态最大。近期把 Copilot Chat 开源进仓库、加 Agent 模式，从编辑器变成 AI 编程载体，所以重新上榜。

**亮点**

- 把 LSP 抽象成通用协议并开放，语言服务不再绑定编辑器，同一条语言服务器能被 VS Code、Neovim、Emacs 共用——这是它生态能铺开的关键一步
- 远程开发把'扩展宿主 + 文件系统'做成可插拔后端层，SSH、容器、WSL 里跑后端，本地只留 UI，前后端之间只传 UI 消息和文件读写请求

**核心功能**

- 多进程拆分：Electron/Chromium 只负责界面渲染，扩展跑在独立的 Node.js 扩展宿主进程里，扩展写崩了编辑器不会跟着挂，两者靠 RPC 通信

- 语言能力走 LSP（语言服务器协议，编辑器与语言分析程序之间的 JSON-RPC 标准接口），语言服务可以是任意语言写的独立进程，Java/Python/TS 各自跑各自的，不共享内存

- 版本策略是可预测的：严格 semver，加 LTS 长支持，企业可以按固定节奏升级而不是被动跟着大版本乱跳，这是它跟很多 PHP 框架最大的定位差异

**核心功能**

- 依赖注入容器会在构建时把配置编译成一份纯 PHP 代码，删掉没用的服务和参数，运行时直接 new 对象，不用反射解析配置
- HttpKernel 用事件驱动一次请求：kernel.request → controller → kernel.response，每一步都能挂监听器改行为，同时在框架内部自带一个纯 PHP 写的 HTTP 反向缓存（支持 ESI、stale-while-revalidate）
- Runtime 组件把入口抽象出来，同一份应用代码能跑在 PHP-FPM、FrankenPHP、RoadRunner、ReactPHP、AMPHP 上，换运行时不用改业务代码
- Messenger 组件做异步消息：把消息投到 AMQP、Redis、Doctrine、SQS 等 transport，带中间件、重试和失败队列，业务代码只管 dispatch
- 路由、校验、权限、DI 都能用 PHP 8 attribute 声明，如 #\[Route\]、#\[IsGranted\]，不用再写一堆 YAML

**适用场景**: 适合中大型团队和需要长期维护的企业系统（电商、SaaS、内容平台），也适合想直接复用单个库的人：比如只拿 symfony/console 写 CLI 工具，或只拿 symfony/mailer 发邮件，不必引入整个框架。Laravel、Drupal、Shopware 这些项目本身就构建在 Symfony 组件之上。

**竞品对比**: 最常对比的是 Laravel。Laravel 更“开箱即用、约定优先”，上手快，自带 ORM/队列/认证一整套；Symfony 更“可拆可换”，组件能单拿，配置更显式，升级更可控。有意思的是 Laravel 底层用的正是 Symfony 的多个组件。另外 Slim、Laminas 更轻量，但生态和组件覆盖远不如 Symfony。

**成熟度**: 生产就绪，已维护十余年，上千贡献者，有 LTS 版本和企业级用户长期验证，文档和升级指南齐全。

**趋势信号**: README 里已在为 Symfony 8.2 招募 backers，说明 8.x 新版本线正在推进；加上 8.0 移除历史包袱、抬高 PHP 版本门槛，引发的升级讨论把老项目重新带回榜单。

### [etcd-io/etcd](https://github.com/etcd-io/etcd)

 `Go` ⭐ +128 今日新增 · 52,640 总星数

> 分布式强一致键值存储，用 Raft 保证多副本数据一致。它是 Kubernetes 控制面的后端数据库，几乎每个 K8s 集群都在运行它。

**亮点**

- 持久化使用 bbolt 单文件 B+ 树和 WAL（预写日志）：写入时先追加 WAL 再修改 B+ 树，崩溃后可以回放日志恢复，不需要独立的数据库进程。
- 把稳定性当作核心功能来维护：仓库自带 robustness 测试框架，会注入网络分区、慢磁盘、随机 kill 进程，检查集群是否仍能正常选主和读写。

**核心功能**

- 用 Raft 复制日志管理多副本：写请求需要多数节点写入磁盘并确认后才返回；leader 宕机后，集群自动重新选主，不需要人工切换。
- MVCC 多版本存储 + gRPC watch 长连接：客户端订阅一个 key 前缀，服务端主动推送变更事件，避免轮询；旧版本通过定期 compaction 清理，否则磁盘会不断增长。
- 只读请求使用 ReadIndex 或 leader 租约（lease read），不必再经过一次 Raft 日志复制，因而不必在每次读时都付出多数派往返的成本。

**适用场景**: K8s 平台的 SRE 和平台工程师会用它保存 kube-apiserver 的全部对象状态；它也被当作分布式锁、选主、服务注册和配置下发的协调组件。

**竞品对比**: 对比 ZooKeeper：etcd 使用 Raft，而不使用 ZAB，并直接提供 gRPC 和 HTTP 接口以及 watch，不需要为每种语言自行编写客户端。对比 Consul：Consul 自带服务发现、健康检查和多数据中心 gossip，而 etcd 只负责 KV 和一致性这一层。最大的差异在于，etcd 是 Kubernetes 的事实标准存储后端。

**成熟度**: 生产可用。CNCF 毕业项目，3.x 版本已经运行十年，是 Kubernetes 的默认存储后端。

**趋势信号**: etcd 3.6 发布，移除了废弃多年的 v2 API，并调整了 Raft 读写路径；同时 Kubernetes 各版本对 etcd 最低版本有硬性要求，运维侧必须跟着升级。

### [mpv-player/mpv](https://github.com/mpv-player/mpv)

 `C` ⭐ +37 今日新增 · 37,926 总星数

> 命令行媒体播放器，本身不做界面，只做播放引擎：FFmpeg 负责解码，libplacebo 用着色器渲染画面。IINA、Celluloid 等图形前端都拿它当内核。

**亮点**

- 故意不讨好人：硬件解码默认关闭、没有 GUI、配置全靠命令行参数和配置文件。因为硬解在各家驱动上坑太多，默认关掉反而少出事，把选择权丢给用户
- 播放器和播放库是同一个东西。libmpv 让 mpv 能嵌进别的程序，IINA（macOS）、Celluloid（Linux）本质就是给这套 C 引擎套了层界面

**核心功能**

- 视频输出不走 GPU 固定管线，改用 libplacebo 跑 GLSL/Vulkan 着色器做缩放和色彩管理，所以能挂第三方着色器（Anime4K、FSRCNNX）实时超分，也能做 HDR 到 SDR 的色调映射
- 核心是纯 C 写的播放引擎，通过 libmpv 的 C API 和 JSON IPC 对外暴露；连自带的屏幕控制器（OSC，那个鼠标一停就浮现的控制条）都是一段 Lua 脚本，键位、UI、行为都能用 Lua/JS 改
- 解码全部交给 FFmpeg（libavcodec/libavformat），硬件解码默认是关的，要手动加 --hwdec 才开；内置 yt-dlp 钩子，贴个视频网站 URL 就能直接播

**适用场景**: 两类人：一是做播放器 app 的开发者，直接链接 libmpv 当内核，自己只写界面；二是键盘党、HTPC 用户和追番党，在终端或极简界面里播片，配 Anime4K 之类的着色器提升画质。

**竞品对比**: 跟 VLC 比，VLC 是大而全的图形播放器，mpv 只有一个引擎、没有界面，画质调节和脚本化能力强得多；跟 ffplay 比，ffplay 只是 FFmpeg 的调试demo，没有着色器渲染、没有脚本、没有配置体系。

**成熟度**: 生产可用：代码血统能追到 MPlayer，二十多年积累，被多个商业/开源前端当内核用；但版本号还在 0.x，官方明说旧版本发布后不再维护，客户端 API 也偶有破坏性改动。

**趋势信号**: 原因不明。37 星/天属于这种老牌项目的日常增长，不是单日爆发；近期 0.40 版本推进的 Vulkan 视频输出和 HDR 支持可能带来了一波关注，但缺少明确事件佐证。

### [openssl/openssl](https://github.com/openssl/openssl)

 `C` ⭐ +26 今日新增 · 31,330 总星数

> OpenSSL 是几乎所有 Linux 发行版和 Web 服务器都在用的 TLS/加密底层库，现在主线已自带 QUIC 实现和 FIPS 认证模块，4.0 大版本线正在推进。

**亮点**

- 同一份代码既服务通用场景又能出 FIPS 140 认证版本，靠的是 provider 隔离——监管环境换 FIPS provider，普通环境用默认 provider，不用维护两个分支
- 从 3.0 起统一为 Apache 2.0 单许可证，去掉了旧版 OpenSSL/SSLeay 双许可证，企业法务审查成本大幅下降

**核心功能**

- QUIC v1（RFC 9000）直接做进 libssl，不用再像以前那样靠 quictls 分支或 ngtcp2 外挂；TLS 1.3 握手与 QUIC 传输在同一套代码里
- Provider 架构：加密算法实现是可插拔的独立模块，运行时加载；FIPS 认证模块就是一个 provider，切换不用重编代码
- libcrypto 可单独使用，openssl 命令行一个工具搞定建密钥、签 X.509 证书/CSR/CRL、算摘要、加解密、搭 TLS/QUIC 测试服务端

**适用场景**: 运维和后台工程师给 nginx、Apache、PostgreSQL、OpenSSH、curl 配 TLS；合规团队在金融、政企环境里需要 FIPS 认证的加密实现；嵌入式/IoT 厂商交叉编译进固件做安全通信。

**竞品对比**: 和 BoringSSL（Google 内部用，不承诺稳定 API）、LibreSSL（OpenBSD 分叉，功能跟进慢）、rustls（Rust 内存安全但生态较新）比，OpenSSL 的差异是唯一同时具备 FIPS 认证模块 + 完整 QUIC + TLS 1.3 的通用库，且是各发行版的默认依赖。

**成熟度**: 极其成熟，20 多年生产验证，全球基础设施默认依赖，文档和迁移指南齐全。

**趋势信号**: 大概率是 4.0 大版本线推进、QUIC 实现进主线带来的关注，加上近期安全公告促使下游集中升级。
