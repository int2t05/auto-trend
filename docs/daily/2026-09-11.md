### [p1neappleXpress/OpenFlux](https://github.com/p1neappleXpress/OpenFlux)

 `Go` ⭐ +355 今日新增 · 1,434 总星数

> 把 TCP 流量塞进 Yandex 文档光标协作消息和 Max 的 WebRTC DataChannel 里，客户端开 SOCKS5、出口节点还原转发的抗审查隧道。

**亮点**

- 不搞域名前置也不自建伪装站，直接把数据通道寄生在第三方 SaaS 的应用层协议上——在线文档的协作光标消息、WebRTC 数据通道。中间人看到的就是访问 Yandex/Max 的正常 TLS 流量，没有可主动探测的私有协议特征。
- RST 抑制刻意做成按源 IP 限定而不是全机 DROP：全机丢 RST 会让所有关闭端口对外显示 filtered 而不是 closed，还会掐断无关连接。README 顺带给出了更干净的做法——把出口节点关进独立 network namespace 或容器。

**核心功能**

- Transport 做成可插拔接口（transport/transport.go），实现接口后在 main.go 的 switch 里注册即可加新通道；自带一层压缩包装器（compressor.go）。目前两个后端：Yandex 文档光标消息、Max 的 WebRTC DataChannel。
- 出口节点用 gVisor 用户态网络栈跑对外 TCP，内核里没有对应 socket，回包会被内核当成无主连接回 RST 打断隧道；项目用按源 IP 限定的 iptables 规则丢 RST，并明确指出 `-m owner --uid-owner` 匹配不生效，因为那批 RST 是内核生成的、没有归属 socket。
- 同一套 Go 核心分别编译成桌面 CLI、Android NDK 二进制、iOS 静态库 liboflux.a（cgo 桥 export_ios.go，给 SwiftUI 客户端链接）；出口节点的 raw socket 按 Linux/Darwin/Windows 分文件实现。

**适用场景**: 网络审查较严地区（README 语境明显指向俄罗斯）不会自己搭服务器的普通用户，装 Android APK 或 iOS TestFlight 直接开全局代理；愿意自建的人需要一台有 root 的 Linux VPS 当出口节点，并接受账号可能被限制的风险。

**竞品对比**: 同类是 Xray/VLESS-Reality、Tor 的 obfs4/meek/Snowflake。区别在于那些方案要么自建一个伪装网站、要么靠志愿者和 CDN 中继；OpenFlux 直接借用现成第三方服务的应用层协议，不需要自有域名。代价是吞吐受载体限制、账号可能被封、完全依赖第三方服务活着。

**成熟度**: 早期项目，没有版本号和正式 release，Max 通道官方标注为实验性且明确警告可能封号，iOS 还在 TestFlight，只适合尝鲜不适合生产。

**趋势信号**: 俄罗斯近期收紧对 VPN/境外流量的管控并强推本土通讯软件 Max，这种“寄生在本土合规服务上”的通道正好绕开白名单式封锁，所以一天涨 355 星。

> Worktrunk 是一个 Rust 写的 Git worktree 命令行工具，专为同时跑多个 AI Agent（Claude Code、Codex）设计，把建/切/删 worktree 简化到跟切分支一样短。

**亮点**

- 把 worktree 的寻址单位从路径换成分支名，路径只是模板产物——这样命令长度和 git branch 一致，抹平了原生 git worktree 的主要痛点
- 用文件系统 reflink 而不是拷贝或软链来共享构建缓存，零拷贝零重建，是纯粹利用底层的取巧做法，其他 worktree 管理工具基本没做

**核心功能**

- wt switch / wt list / wt remove 三条核心命令按分支名寻址 worktree，路径由配置模板自动算出，不用记 ../repo.feat 这种相对路径；wt switch -c -x claude feat 一条命令就建好 worktree 并直接拉起 Claude Code
- wt step copy-ignored 用文件系统写时复制（APFS / btrfs / XFS 的 reflink）把 target/、node_modules/ 这类忽略目录共享给新 worktree，十个 worktree 不用各建一份也不用真的拷贝，省磁盘也省构建时间
- 生命周期 hooks（create、pre-merge、post-merge 等）+ 每分支变量 + hash_port 模板过滤器，能自动给每个 worktree 分配独立端口跑 dev server；wt list --full 还会拉取每个分支的 CI 状态并用 LLM 生成一句变更摘要

**适用场景**: 面向同时开 5~10 个 AI 编码 Agent 的开发者：每个 Agent 一个 worktree 互不干扰，各自跑独立端口的 dev server，跑完用 wt merge 一条命令 squash、rebase、合并、删分支。也适合要快速跳到某个 PR 分支的人（wt switch pr:123）。

**竞品对比**: 直接竞品是原生 git worktree 和 gh 的 worktree 扩展，但那些只管建目录不管工作流；相比 Conductor 这类 Mac GUI 应用，Worktrunk 是纯 CLI，可脚本化、能塞进 Zellij/tmux 的多 Agent 面板里。

**成熟度**: 发布不到一年但迭代活跃，MIT/Apache 双协议、有 CI 和 Codecov、文档站完整，作者在积极收 issue，但功能面和命令语义可能还在调整。

**趋势信号**: Claude Code、Codex 这类能长时间无人值守跑任务的 Agent 普及后，开发者开始同时开 5~10 个 Agent，worktree 从冷门功能变成刚需，Worktrunk 正好卡在这个多 Agent 并行工作流的窗口上。
